## 实验 10-1 ★★：共享上下文中的多角色转换——系统提示词与 Skill 的对比

- **原书位置**：§「共享上下文的多 Agent 协作」（`transfer_to_agent` 与 Skill 的对比表之后）
- **实验目标**：在**同一模型、同一用户任务、同一工具实现、同一份角色规程、全量共享轨迹**的受控条件下，比较两种角色规程载体——**替换 system prompt（`transfer_to_agent`）** 与 **按需加载 Skill**——在上下文/KV Cache 复用、工具可见性、约束能力三个维度上的差异。
- **前置条件**：
  - 一个支持多角色系统提示词切换的 Harness：移交时能保存历史、加载目标角色的提示词与工具集、再继续调用；
  - 一个支持 `load_skill(name)` 的实现，读取的 `SKILL.md` 能作为 tool result 进入共享轨迹（即第二章的 Skills 机制）；
  - 五个角色的同一份角色规程、同一套工具实现，两条路径共用。
- **操作步骤**：
  1. 固定共同任务：查找中国 2021—2023 年新能源汽车销量、计算 CAGR、写不超过 120 字的投资人摘要。
  2. 路径一（系统提示词切换）：实现 triage（默认入口）、research、coding、data_analysis、writing 五种角色；每个角色**只暴露自己的专属工具和 `transfer_to_agent`**；移交时保存历史、加载目标角色提示词/工具集，再继续调用。
  3. 路径二（Skill）：system prompt 和完整工具全集**全程固定**；模型按需调用 `load_skill(name)`，Skill 内容作为 tool result 追加到轨迹末尾；硬权限改由 harness 中的规则保证。
  4. 同一任务跑两条路径，逐轮记录：请求前缀是否被复用（KV Cache 命中）、当前可见工具集、越界工具调用次数、总 token 与首 token 延迟。
  5. 保留原书提到的「旧实现」作为路径一这一分支的基线（原书：「旧实现保留在配套项目中，作为这一实验分支的基线」）。
- **关键代码或配置**（逐字摘录原书 实验 10-1）：

  > **共同任务与变量**：两条路径都使用同一模型、同一用户任务、同一工具实现、同一份角色规程和全量共享轨迹。任务是查找中国 2021—2023 年新能源汽车销量、计算 CAGR、写不超过 120 字的投资人摘要。

  > **路径一：系统提示词切换**。五种角色为 triage（用户需求收集，默认入口）、research（信息检索）、coding（编程）、data_analysis（数据分析）和 writing（写作）。每个角色只看到自己的专属工具和 `transfer_to_agent`；调用移交时保存历史、加载目标角色提示词/工具集，再继续调用。

  > **路径二：Skill**。system prompt 和完整工具全集在整个会话中固定；模型按需调用 `load_skill(name)`，读取的 `SKILL.md` 作为 tool result 进入共享轨迹。这样静态前缀不因角色变化而重写，但工具仍然可见，硬权限由 harness 中的规则保证。

  原书对照表（摘录，完整表见 §共享上下文的多 Agent 协作）：

  | 选择 | 角色规程的载体 | 工具可见性 | 上下文/KV Cache 影响 | 约束能力 |
  | --- | --- | --- | --- | --- |
  | `transfer_to_agent` | 替换当前 system prompt，并通常替换工具集 | 只暴露当前角色工具 | 每次切换都改变请求前缀；从变化点起的前缀缓存通常无法复用 | 强：越界工具可在 schema 层不可见 |
  | Skill | 固定 system prompt 中的 Skill 目录，按需把 `SKILL.md` 追加到轨迹 | 通常固定暴露工具全集，或使用稳定的工具搜索入口 | 静态前缀保持不变；Skill 内容成为末尾轨迹，已有前缀可继续复用 | 弱：Skill 是行为指令，硬权限仍需 Harness 门 |

- **预期结果与判读方法**：
  - 判读一（成本）：路径二应表现为**静态前缀可继续复用**，路径一表现为**每次切换都改变请求前缀、从变化点起的前缀缓存无法复用**。把「缓存命中 token 占比 / 首 token 延迟」对角色切换次数作图，两条成本曲线应当分离。
  - 判读二（约束）：路径一在 schema 层让越界工具不可见；路径二里越界工具**仍然可见**。因此越界调用次数衡量的不是模型是否守规矩，而是 **Harness 门是否生效**。
  - 判读三（质量）：两条路径共享同一份角色规程与全量轨迹，最终摘要质量本不应有系统差异；若出现明显差异，优先怀疑角色切换时规程未完整加载，或 Skill 内容实际上没被读进轨迹。
- **常见陷阱**：
  - 把 Skill 当权限机制用。原书明确「Skill 是行为指令，硬权限仍需 Harness 门」——只加 Skill 而 harness 无规则，工具越界不会被拦住。
  - 变量不齐：两条路径若换了模型、工具实现或角色规程，观察到的差异无法归因到「角色载体」这一个变量上。
  - 只比最终摘要质量、不记缓存与延迟，会把本实验最有价值的成本差异丢掉。
  - 共享轨迹带来的角色惯性：后续角色能读到前序角色的规程与思考，容易被上一个身份带跑（正是思考题 1 的场景）。
- 〔精读批注〕协作结构上这是**共享上下文 + 单 Agent 多角色**，不是真正的多 Agent 并行——同一时刻只有一条思维链，角色以时间片轮转。因此它天然拿不到本章那条核心判据（协作是否引入单 Agent 生成时无法获得的新信息）所要求的增量；它能拿到的收益只是「让每个阶段用上最合适的规程与工具集」。失败模式落在两处：**角色惯性**（语义问题，继承历史把注意力拉回上一个身份）与**前缀缓存失效**（经济问题，每次切换都从变化点起重算）。原书给出的选择规则值得当作待检验假设：角色差异在知识、流程、写作风格 → 用 Skill；角色差异涉及权限、工具隔离、合规边界 → 用独立 Agent 或 `transfer_to_agent`，并在 Harness 层用代码限制工具调用。建议动手时专门设计一个含敏感动作的任务，检验 Harness 门是否真的补上了 Skill 缺失的那部分约束力。

## 实验 10-2 ★★：书籍翻译 Agent

- **原书位置**：§「管理者模式：中心化协调」→ 顺序协调形态
- **实验目标**：用管理者模式拆解「翻译一本技术书」这类**长程、需要全局一致性**的任务，验证**任务分解 + 责任分离 + 上下文隔离**能否同时解决上下文超限、术语不一致与注意力涣散三个问题，并对比单 Agent 与管理者模式在翻译质量、执行效率、资源消耗上的差异。
- **前置条件**：
  - 一本图文并茂、包含代码的技术书籍作为翻译对象（原书实验要求第 1 条）；
  - 一个可被多个 Agent 读写的共享文件系统（术语表、译文、审校报告的落盘位置）；
  - Manager 能并行或串行启动多个 Translation Agent 实例。
- **操作步骤**：
  1. 选定翻译对象，切分章节，明确目标读者水平与语言风格（翻译指南）。
  2. 实现 Glossary Agent：接收全书内容，识别重复出现的专业术语，搜索专业词典和翻译规范，生成结构化术语对照表（JSON/CSV，含英文术语、中文翻译、词性、使用语境），写入共享文件系统后即可销毁释放资源。
  3. 实现 Translation Agent：接收当前章节 + 术语对照表 + 翻译指南，逐章翻译；对照表中的术语严格使用规定译法，新术语推断翻译并标记待审查；译文写入文件系统（如 `chapter1_zh.md`）。
  4. 实现 Proofreading Agent：接收所有译文与术语表，逐一验证术语翻译是否统一、识别前后不一致之处、检查流畅性与可读性，产出审校报告写入文件系统。
  5. 实现 Manager Agent：上下文中只保留任务描述、执行计划、各 Agent 的调用记录与进度状态，**不保存完整翻译内容**，只维护文件索引；根据审校报告把特定章节发回 Translation Agent 修订。
  6. 记录每个 Agent 的上下文消耗，验证管理者模式控制上下文膨胀的有效性；再与单 Agent 直译做同书对比。
- **关键代码或配置**（逐字摘录原书 实验 10-2 的角色定义）：

  > - **Glossary Agent**（术语对照表 Agent）：接收全书内容，识别重复出现的专业术语，搜索专业词典和翻译规范，生成结构化术语对照表（JSON/CSV 格式，包含英文术语、中文翻译、词性、使用语境）。完成后写入共享文件系统，Agent 即可销毁释放资源

  > - **Translation Agent**（章节翻译 Agent）：接收当前章节、术语对照表和翻译指南（目标读者水平、语言风格），翻译为流畅的中文。遇到对照表中的术语严格使用规定译法，遇到新术语则推断翻译并标记为待审查。每个实例在独立上下文中工作，互不干扰。译文写入文件系统（如 `chapter1_zh.md`）。Manager 可并行或串行启动多个实例

  > - **Manager Agent**：上下文中主要保存任务描述、执行计划、各 Agent 的调用记录和进度状态。不保存完整翻译内容（这些存在文件系统中），只维护文件索引。根据审校报告，Manager 可以把特定章节发回 Translation Agent 修订

  原书实验要求（逐字）：

  > 1. 选择一本图文并茂、包含代码的技术书籍作为翻译对象
  > 2. 实现 Manager、Glossary、Translation、Proofreading 四种 Agent
  > 3. 记录每个 Agent 的上下文消耗，验证管理者模式控制上下文膨胀的有效性
  > 4. 对比单 Agent vs 管理者模式在翻译质量、执行效率、资源消耗方面的差异

![图10-5 书籍翻译 Agent 架构](../images/fig10-5.svg)

> **图 10-5 解读**：该图给出书籍翻译 Agent 的架构（原书 实验 10-2）——Manager Agent 只持有任务描述、执行计划、调用记录与进度状态，Glossary / Translation / Proofreading 三类 Agent 通过共享文件系统交换术语表、译文与审校报告，各自在精简独立的上下文中工作。

- **预期结果与判读方法**：
  - 上下文曲线：Manager 的上下文应**随章节数近似持平**（只维护索引），单 Agent 方案则随章节数线性膨胀——这是本实验最直接的可判读信号。
  - 一致性指标：跨章节术语一致率、审校报告中的不一致条目数；若 Glossary 产出的对照表未被 Translation 真正读取，一致率会回落到单 Agent 水平。
  - 质量与成本对照：按实验要求第 4 条，在翻译质量（人工抽样评分）、执行效率（墙钟时间）、资源消耗（总 token）三个轴上对比单 Agent 与管理者模式。
- **常见陷阱**：
  - 让 Manager 顺手「看一眼译文」——只要译文进了 Manager 上下文，上下文隔离的设计就失效了。
  - 术语表格式不固定：Glossary 输出的 JSON/CSV 字段若不稳定，Translation 只能靠猜，跨章一致率不会真的提升。
  - 忽略「新术语标记待审查」这一环：新术语不回流到术语表，后文遇到同一术语会再次自由发挥。
  - 审校只查术语、不查流畅性，会把「术语对但读起来像机翻」的稿件判为通过。
- 〔精读批注〕这是**管理者模式 + 不共享上下文**的教科书形态：四种 Agent 之间没有共享轨迹，全部靠共享文件系统交换**路径而不是内容**（第四章「文件路径作为通用接口」）。它的失败模式集中在**接口规范**上——术语表的字段结构、译文的命名规则、审校报告的定位粒度，任何一项含糊都会在几十章的量级上被放大成系统性不一致；这正是原书说的「接口规范、数据格式和通信协议的设计变得至关重要」。成本上，它用「多次小上下文调用」替换「一次超长上下文调用」，token 总量未必更低（每个 Translation 实例都要重复读术语表与指南），换来的是**每章上下文可控**与**可并行**；动手时应把这两笔账分开记，否则会误判管理者模式的成本优势。另一个值得单独设计的对照组是「把 Glossary 换成更强的模型」——按 MetaGPT 的解耦逻辑，只要它发布的术语表仍符合规范，其他 Agent 无需修改。

## 实验 10-3 ★★★：自主编排的电话 + 电脑 Agent

- **原书位置**：§「管理者模式：中心化协调」→ 并行协调形态
- **实验目标**：让 Computer Agent 在**没有额外 Manager 进程**的前提下自主决定是否调用 Phone Agent，验证「异构双 Agent 的点对点协作 + 真正并行 + 双向状态反馈」能否把用户从逐项打字中解放出来，并比较固定模式（并发基线）与自主模式（主实验）的差异。
- **前置条件**（逐字）：**本实验综合运用第六章的 Computer Use 和语音 Agent 技术。** 因此需要一条可用的语音回路（ASR + LLM + TTS、WebRTC）与一个可被程序驱动的浏览器会话。
- **操作步骤**：
  1. 搭建两个独立 Agent：Computer Agent（浏览器操作 + 编排者）与 Phone Agent（ASR、LLM、TTS 与实时对话）。
  2. 定义结构化消息的信封（发送者、接收者、类型、内容），通道使用点对点工具或消息总线。
  3. 跑**固定模式（并发基线）**：预先启动两个 Agent，验证独立 ReAct 循环、双向通信与真正并行。
  4. 跑**自主模式（主实验）**：只启动 Computer Agent，由它根据页面、已知信息和任务需要自主决定是否调用 `initiate_phone_call_agent(purpose, required_info)`；调用后把任务目的、待收集字段及格式约束作为**独立上下文**交给 Phone Agent。
  5. 实现闭环：Phone Agent 逐项提问、抽取并校验回答，Computer Agent 同时截屏、理解页面并填写字段；每收到一个有效值就发送 `info_collected`，Phone Agent 不等待网页填写完成便询问下一项；Computer Agent 反馈 `fill_error` 或页面状态；格式错误发送 `format_invalid` 并重问；超过重试次数或页面异常则安全暂停；信息收集完成后发送 `task_completed`。
  6. 记录消息时序、自主启动决策、延迟、成功率与资源消耗，比较两种模式。
- **关键代码或配置**（逐字摘录原书 实验 10-3）：

  > **系统架构**：Computer Agent 负责浏览器操作，也是本实验的编排者；Phone Agent 负责 ASR、LLM、TTS 和实时对话。两者通过点对点工具或消息总线交换结构化消息（发送者、接收者、类型、内容）。不需要额外的 Manager 进程：Computer Agent 可以像调用工具一样调用 Phone Agent。

  > - **固定模式（并发基线）**：预先启动两个 Agent，验证独立 ReAct 循环、双向通信和真正并行。
  > - **自主模式（主实验）**：只启动 Computer Agent。它根据页面、已知信息和任务需要，自主决定是否调用 `initiate_phone_call_agent(purpose, required_info)`；不要用“字段数量超过阈值”的 Python 规则代替模型决策。

  > **并行与闭环**：Phone Agent 通过 WebRTC 逐项提问、抽取并校验回答；Computer Agent 同时截屏、理解页面并填写字段。每收到一个有效值就发送 `info_collected`，Phone Agent 不等待网页填写完成便询问下一项；Computer Agent 反馈 `fill_error` 或页面状态，Phone Agent 据此调整话术。格式错误发送 `format_invalid` 并重新询问，超过重试次数或页面异常则安全暂停。信息收集完成后发送 `task_completed`，Computer Agent 通过校验后提交表单。异常时取消仍在运行的对端，关闭浏览器、音频轨道和通话；真人语音须显式同意，提交须显式授权。

  消息类型清单（供实现时对齐）：`initiate_phone_call_agent(purpose, required_info)`、`info_collected`、`fill_error`、`format_invalid`、`task_completed`。

![图10-7 Phone 与 Computer 双 Agent 架构](../images/fig10-7.svg)

> **图 10-7 解读**：该图给出 Phone 与 Computer 双 Agent 架构（原书 实验 10-3）——Computer Agent 既是浏览器操作者也是编排者，Phone Agent 负责实时语音链路，两者以点对点工具或消息总线交换带类型字段的结构化消息，不需要额外的 Manager 进程。

- **预期结果与判读方法**：
  - 并行判据（实验要求第 2 条）：必须能证明「问下一个」和「填上一个」**真正重叠**——从消息时序上看，`info_collected` 与下一轮提问的时间间隔应小于网页填写耗时，否则只是轮流执行。
  - 自主性判据：自主模式中 `initiate_phone_call_agent` 的触发必须来自模型决策；原书明确禁止用「字段数量超过阈值」的 Python 规则代替——一旦用规则替代，实验测的就不是自主编排。
  - 闭环判据：格式错误能触发 `format_invalid` 并重问、页面异常能安全暂停、异常时对端被取消且浏览器/音频轨道/通话被清理。
- **常见陷阱**：
  - 用启发式规则替代模型决策（最常见的跑偏），使「自主模式」名不副实。
  - 把 Phone Agent 做成被动应答：它必须能主动逐项推进、在收到 `fill_error` 后调整话术，否则并行退化为串行问答。
  - 忘记资源清理与授权边界：原书要求异常时取消对端、关闭浏览器与音频轨道，「真人语音须显式同意，提交须显式授权」。
  - 只统计最终成功率、不记录消息时序，就无法回答「并行到底省了多少时间」。
- 〔精读批注〕这是本章唯一一个**异构双 Agent 且无中心 Manager**的编排实验：Computer Agent 同时扮演「执行者」和「编排者」，Phone Agent 是被调用的对端——用原书的话说，「Computer Agent 可以像调用工具一样调用 Phone Agent」，正好对应管理者模式里「把每个专门 Agent 建模为 Manager 可调用的工具」的最小形态。协作结构上它是**不共享上下文 + 点对点消息**，两个 Agent 各有一条独立 ReAct 循环，靠信封（发送者/接收者/类型/内容）对齐状态。它的失败模式很典型：**双向反馈不对称**（一边持续产出、另一边不回压），以及**取消路径未实现**（异常时留下悬挂的浏览器会话或通话）。成本与延迟上，这条路径的收益来自「人的输入带宽」——用语音的连续确认替换逐项打字；代价是引入了一条实时音频链路，整体延迟由**较慢的一方**决定，因此消息时序记录比成功率更能说明它是否真的成立。

## 实验 10-4 ★★★：同时从多个网站搜集信息的 Agent

- **原书位置**：§「管理者模式」→ 并行协调形态
- **实验目标**：探索**多个同构 Agent 的并行搜索**，通过中心协调实现任务完成与资源优化；重点不在异构分工，而在**并行启动、实时监控、级联终止、失败处理**四件事如何在消息总线与状态表上落地。
- **前置条件**（逐字）：**建议先了解第六章的事件驱动与中断机制。** 另需一个可并发启动多个浏览器会话的运行环境，以及一个消息总线。
- **操作步骤**：
  1. Manager Agent 根据任务需求动态创建 10 个 Computer Use Agent 实例，每个实例对应一个学院网站；每个实例是独立进程或线程、拥有独立浏览器会话，启动时传入目标网站 URL、要搜索的教师姓名、任务标识符（用于消息路由）。
  2. 每个 Agent 执行过程中定期发送状态更新（“正在加载网站”“正在解析教师名录”“未找到目标，任务完成”“找到匹配，详细信息如下”）；Manager 通过消息总线接收并维护一张任务状态表。
  3. 实现级联终止：某个 Agent 发送 `{"type": "target_found", "agent_id": "agent_3", "data": {...}}` 后，Manager 立即向所有仍在运行的 Agent 发送 `{"type": "terminate", "reason": "target_found_by_agent_3"}`，等待所有确认（或超时）后汇总；终止必须优雅，不留悬挂进程或未关闭资源；同时处理竞态条件。
  4. 实现失败处理：为每个 Agent 设置超时（如 2 分钟），超时视为失败；错误隔离，不影响其他 Agent；全部完成后汇总——只要有 Agent 成功就返回信息，全部失败则报告“未找到目标教师”及各失败原因的统计。
  5. 记录并对比并行执行与串行执行的时间差异。
- **关键代码或配置**（逐字摘录原书 实验 10-4）：

  > **问题**：给定一所大学的多个学院网站，要求在各学院的教师名录页面中查找指定教师（如“张伟”），找到后返回其所在学院、职位、研究方向等信息。

  > **3. 级联终止**：假设负责计算机学院的 Agent 找到了目标教师，它发送 `{"type": "target_found", "agent_id": "agent_3", "data": {...}}`。Manager Agent 收到后立即向所有其他仍在运行的 Agent 发送 `{"type": "terminate", "reason": "target_found_by_agent_3"}`，每个收到终止消息的 Agent 优雅停止并发送确认。Manager Agent 等待所有确认（或超时）后汇总结果。

  > **概念补充：什么是竞态条件？** 假设 Agent A 和 Agent B 几乎在同一毫秒内各自找到了目标教师，它们同时向 Manager Agent 报告“我找到了！”。如果 Manager Agent 处理不当——比如收到 A 的报告后开始汇总结果，但紧接着又收到 B 的报告触发了第二次汇总——就可能产生重复的结果或互相矛盾的状态。解决方法通常是使用“锁”机制：第一个报告到达后立即锁定状态，后续报告被识别为重复并忽略。

  原书实验要求（逐字）：

  > 1. 实现能动态启动多个并行 Agent 的 Manager Agent
  > 2. 基于 browser-use 等开源项目实现 Computer Use Agent
  > 3. 实现消息总线支持 Manager Agent 与多个子 Agent 双向通信
  > 4. 实现成功后的级联终止机制，确保找到目标后所有其他 Agent 快速停止
  > 5. 处理各种异常情况（网站访问失败、解析错误、全部未找到）
  > 6. 记录和对比并行执行与串行执行的时间差异，验证并行化带来的性能提升

![图10-8 并行 Web Scraping 架构](../images/fig10-8.svg)

> **图 10-8 解读**：该图给出并行 Web Scraping 架构（原书 实验 10-4）——Manager Agent 动态创建多个 Computer Use Agent 实例，每个实例持有独立浏览器会话并经消息总线上报状态；一旦某个实例报告 `target_found`，Manager 广播 `terminate` 级联终止其余实例后汇总。

  - 并行收益：实验要求第 6 条的并行 vs 串行时间差；注意 10 个实例的墙钟时间下限由最慢/超时的实例决定（超时设为 2 分钟，故最坏情况是「等到超时」）。
  - 级联终止质量：从 `target_found` 到所有确认返回（或超时）的耗时分布，以及终止后是否残留进程与浏览器会话。
  - 竞态判据：日志中是否出现**双重汇总**；压力测试手段是人为制造两个 Agent 几乎同时命中，检查锁是否生效。
  - 失败处理：至少覆盖网站不可访问、页面结构与预期不符、全部未找到三类异常，并检查错误是否被隔离。
- **常见陷阱**：
  - Manager 的汇总逻辑不幂等：两个几乎同时到达的成功事件触发两次汇总，产出重复或矛盾的结果（原书已点明）。
  - 终止不优雅：只杀进程不清理资源，留下悬挂浏览器会话。
  - 把「未找到」当成错误：全失败与「搜完确实没有」是两种结论，汇总口径要分开。
  - 只保证「找到即停」，不考虑「一个 Agent 的发现是否让其他 Agent 的工作变得无意义」之外的情形——若多个学院都有同名教师，级联终止反而会丢掉其他匹配。
- 〔精读批注〕这是**管理者模式 + 同构并行**的典型：协作结构是星型，Manager 是唯一控制点，子 Agent 之间不通信（对比实验 10-3 的点对点异构协作）。失败模式几乎全部落在控制平面上：**竞态**（汇总不幂等）、**终止强度**（优雅 vs 强制，对应 SIGTERM/SIGKILL）、**错误隔离**（一个网站挂掉不应拖垮全局）。它同时是本章「并行协调形态」与「执行终止」「实时监控」三节的落地实验——原书说的三种状态获取方式中，本实验用的是「用消息传递获取状态」（`status_update`），而「轨迹持久化」与「进度文件」则给出成本更低的替代路径（读文件而非收消息），动手时值得做一个对照：把状态上报从消息总线换成 `progress.md` + 最后修改时间判定卡住，比较 Manager 的上下文开销与响应延迟。成本上要留意原书那句提醒——多 Agent 的收益必须覆盖数倍乃至一个数量级的额外开销；用一个 10 实例的搜索任务做成本账最直观：token 与并发额度是线性的，而时间收益受最慢实例约束。

## 实验 10-6 ★★★：语音狼人杀 Agent 系统

- **原书位置**：§「Agent 社会」→ 信息不对称下的策略博弈：狼人杀
- **实验目标**：构建多 Agent 系统让 AI 扮演狼人杀中的各种角色、与真人玩家**通过语音**游戏，同时考验推理、角色扮演与实时交互能力；架构上对应本章「法官 + 信息权限控制」的中心化设计，与完全去中心化的 AI 小镇构成对照。

- **操作步骤**：
  1. 实现游戏状态管理：法官（代码驱动，非 LLM）维护玩家列表（用户席位 + AI 混合）、身份、阵营、生存状态、游戏阶段（夜晚/白天/投票/结算）与历史事件记录。
  2. 实现信息权限控制：法官在调用每个角色 Agent 时，只传递该角色应当看到的信息（狼人知道同伙、村民不知道；预言家的查验结果只有自己知道）。
  3. 配置各角色的推理与策略提示词：狼人伪装策略、预言家身份证明、村民逻辑推理。
  4. 组局并跑通完整回合：6-8 人局（1 个用户席位 + 5-7 个 AI Agent）、2 狼人 + 1 预言家 + 1 女巫 + 其余村民，用户席位随机分配角色。
  5. 按验收标准逐条核对：至少 3 个完整回合、发言符合角色与策略、狼人能有效隐藏、预言家能在合适时机跳出、村民推理基于逻辑而非随机猜测、结束时能正确判断胜负。
- **关键代码或配置**（逐字摘录原书 实验 10-6 的策略提示词）：

  > - **狼人伪装策略**：提示词中包含常见的话术和策略——“像普通村民一样发言，可以表达对某些玩家的怀疑，但不要过于激进以免引起注意。如果有预言家跳出来说验到你是狼人，你可以反咬对方是悍跳的假预言家。投票时尽量跟票（投大多数人投的目标），避免成为异类。”
  > - **预言家身份证明**：当多个玩家声称自己是预言家时——“对比你和对方的验人信息，指出对方信息中的矛盾或不合理之处。如果对方声称验过的某个玩家，在后续行为中明显不符合其声称的身份，那就是破绽。请求女巫配合验证。”
  > - **村民逻辑推理**：“分析每个玩家的发言是否自洽，留意那些急于带节奏、模糊身份、频繁改变立场的玩家。关注投票行为——狼人往往集中票数投给对他们威胁最大的好人。不要随机怀疑，每个推理都应基于具体事实和逻辑。”

  原书验收标准（逐字）：

  > - 设置 6-8 人游戏局（1 个用户席位 + 5-7 个 AI Agent）；用户席位可以是授权真人，也可以是使用真实 LLM、工具和语音回环的独立模拟用户
  > - 角色配置：2 只狼人、1 个预言家、1 个女巫、其余为村民，用户席位随机分配角色
  > - 模拟用户只能看到该座位获准看到的私有/公开上下文；其发言和动作必须经过真实 LLM 工具调用 → 音频 → 真实 ASR 的边界
  > - 游戏能正常进行至少 3 个完整回合（夜晚-白天-投票循环）
  > - AI Agent 的发言和行为符合其角色身份和游戏策略
  > - 狼人 Agent 能有效隐藏身份
  > - 预言家 Agent 能在合适时机跳出并公布验人信息
  > - 村民 Agent 的推理基于发言和行为的逻辑分析，而非随机猜测
  > - 游戏结束时能正确判断胜负

> **图 10-11 解读**：该图给出语音狼人杀 Agent 系统（原书 实验 10-6）——代码驱动的法官掌握全局状态并按角色分发各自应知的信息，各角色 Agent 只拿到该角色可见的上下文，真人或模拟用户席位经真实 LLM 工具调用 → 音频 → 真实 ASR 的边界参与游戏。

- **预期结果与判读方法**：
  - 权限判据：日志中每个角色 Agent 收到的上下文必须严格等于该角色应见集合——一旦法官多传了信息（例如把狼人名单发给村民），整局的可信度作废。
  - 策略判据：狼人是否按提示词隐藏（不激进、跟票）、预言家是否在合适时机跳出、村民的怀疑是否都能回溯到具体发言或投票证据。
  - 边界判据：模拟用户席位的发言必须真的走完 LLM 工具调用 → 音频 → ASR 一圈；若在其他环节注入文本，验收条件里的「真实边界」就不成立。
  - 胜负判据：游戏结束时能正确判断胜负，且至少跑满 3 个完整回合（夜晚-白天-投票循环）。
- **常见陷阱**：
  - 让法官由 LLM 担任：法官必须代码驱动，否则信息权限控制本身就成了一个可被说服的模型判断。
  - 用文本通道旁路语音链路，使实验退化为纯文本狼人杀。
  - 把「AI 会骗人」当成策略涌现的证据——伪装是提示词直接写明的行为，不是自发策略。
  - 忽略发言时序与投票统计，只做定性观察，导致「狼人是否有效隐藏」无法判读。
- 〔精读批注〕这是本章**中心化设计与信息不对称**的组合实验：法官不参与推理，只做两件事——维护状态机与**按角色裁剪上下文**，本质上是在多 Agent 系统中手工实现了一套最小权限（least privilege）机制，与本章「不共享上下文」的原则同构。它同时给了「对等协作需要主动制造多样性」一个反面案例：狼人、预言家、村民用的是同一底层模型，仅靠**提示词差异 + 信息差异**区分角色——如果去掉信息权限控制，全部 Agent 会迅速趋同，正是失败模式三描述的共因失效。失败模式上最值得观察的是**欺骗与自我欺骗的边界**：Agent 的“推理”未必真的基于证据链，而可能只是复述提示词里写好的策略模板；验收标准里「村民 Agent 的推理基于发言和行为的逻辑分析，而非随机猜测」正是为此设的判据。成本与延迟上，语音回路把每次发言变成一次端到端音频往返，实时性是本实验最硬的约束——它决定了整局游戏的节奏上限，也让「并行」在这里失去了用武之地（发言天然是串行的）。
