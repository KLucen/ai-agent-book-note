# 第4章 工具（实验解读）

> [!info] 使用说明
> 本章共 5 个实验（4-1～4-5）：1 个工具发现实验 + 3 个 MCP 工具服务器实验（感知/执行/协作）+ 1 个多模态范式对比。每节含 **目的 / 设计 / 关键结论 / 精读批注** + **动手记录区**。
> 配套代码：开源仓库 `github.com/bojieli/ai-agent-book` 的 `chapter4/` 目录。**本章所有实验均基于 MCP 协议构建工具**——这本身是练手 MCP 客户端/服务端实现的好机会。多数实验需要 API 额度（部分可用本地模型替代，如 4-1 用 Qwen3-4B）。

## 实验 4-1 ★★★：主动工具发现

- **原书位置**：§「模型原生的主动工具发现」之后
- **目的**：验证主动工具发现对小参数量模型的显著价值——**用 Qwen3-4B 访问 120+ 个工具**（来自实验 4-2 构建的感知工具 MCP 服务器）。
- **实验设置**：一组需要**跨领域工具协作**的任务，例如：
  - 「查询苹果公司最新股价，搜索相关新闻分析原因」（需 Yahoo Finance + Web Search）
  - 「在 arXiv 上搜索关于 transformer 的最新论文，下载排名前三的论文」（需 arXiv Search + File Download）
  - 「分析 GitHub 上某个仓库的贡献者统计，生成可视化报告」（需 GitHub + Code Interpreter）
- **对照组**：把 120+ 工具的**完整 schema 一次性注入 system prompt（超 50K tokens）**。4B 模型在这么长的上下文下指令遵循能力严重退化，出现典型问题：面对「查询股价」可能错选 Web Search 而非专门的 Yahoo Finance 工具，或「忘记」列表中的某些工具导致任务失败。
- **实验组**：混合方案（MCP-Zero 主动发现思想 + 工具搜索工具式实现）：① system prompt 只保留 `web_search`、`code_interpreter` 与 `discover_tools` 元工具；② `discover_tools` 接受自然语言需求（如「我需要查询股票价格的能力」），用嵌入向量相似度返回 3–5 个候选工具及完整 schema；③ 新工具定义**追加到对话历史（作为 user message）**，Agent 状态栏更新工具名称列表；④ 引导模型在遇到能力缺口时主动调用 `discover_tools`。
- **预期观察**：**准确率与任务完成率显著提升**。主动工具发现不仅帮能力较强的大模型应对成千上万工具，更让**小参数量模型在上百工具场景下保持可用**。
- 〔精读批注〕这个实验最值得亲手量的是「对照组的失败模式分布」：是**选错工具**（语义相近干扰）还是**漏用工具**（长上下文里被忽略）？两者的修复手段不同——前者要靠更好的分类/层次化组织，后者要靠按需加载。也建议记录「`discover_tools` 调用次数 / 任务」与 token 曲线，验证「发现成本 < 全量注入成本」的交叉点在哪里。

## 实验 4-2 ★★：感知工具 MCP 服务器

- **原书位置**：§「感知工具」之后
- **目的**：构建一套覆盖五类感知场景的 MCP 服务器，作为后续实验（4-1 的 120+ 工具来源）与第 5 章「七个核心工具」对照的基础。
- **五类感知场景**：
  1. **搜索**：网络搜索、本地知识库搜索、文件下载；
  2. **多模态理解**：网页阅读、PDF/Word/PPT 等文档提取、图片 OCR 与 AI 分析、音视频转录与分析；
  3. **文件系统**：文件读取与搜索、目录浏览、文件操作（移动/复制/删除等——严格说属执行工具，但通常与文件读取打包在同一 MCP 服务器）；
  4. **公开数据源**：天气、股价、汇率、Wikipedia、ArXiv 等免费 API；
  5. **私有数据源**：日历、Notion 等需要授权的个人数据。
- **关键结论**：这些工具大多基于免费开放 API，无需注册即可使用；MCP 生态已有大量现成感知工具服务器可用。**第 5 章将论证：其中大部分功能可以用七个核心工具配合 Skill 文档来覆盖。**
- 〔精读批注〕这就是本章「形态 vs 数量」争论的实操场：本实验刻意做**很多专用工具**，第 5 章则用**少量通用工具 + Skill** 达到同样覆盖——两次实验对照着做，比读任何论证都更能建立直觉。建议把每个工具的描述、返回格式、截断策略记录成一张表，作为自己写工具时的模板库。

## 实验 4-3 ★★：多模态信息提取：三种技术范式的对比分析

- **原书位置**：§「多模态感知」之后（`multimodal-agent` 项目）
- **目的**：在统一框架内系统比较三种多模态策略。
- **设计**：通过 `demo.py` 把**同一个多模态文件（如含图表的 PDF 报告）与同一个问题**分别交给三种模式处理，观察表现差异：
  - **原生多模态模式**（模型直接看图/版面）；
  - **提取为文本模式**（OCR/解析后喂语言模型）；
  - **工具化模式**（`analyze_pdf`/`analyze_image` 等工具，内部调用多模态模型）。
- **关键结论（三者权衡）**：
  - **原生多模态**：凭借对视觉与空间信息的深刻理解，**分析图表、理解文档布局等任务上表现最佳**；
  - **提取为文本**：处理**纯文本占主导**的文档时**成本效益最高**，但完全无法处理需要视觉信息的查询；
  - **工具化**：在**交互式场景**中展现灵活性——以较低成本处理大多数初步查询，需要时再调用工具做高成本深度分析；但在**需要一次性端到端深度理解**的场景下不如原生模式。
- 〔精读批注〕这个实验的结论可以直接变成**路由策略**：先用工具化模式做「廉价试探」（问题 + 摘要），只有当问题明显依赖布局/空间关系（表格行列、UI、图表趋势）时才升级到原生多模态。建议记录三种模式的**每问 token 成本与准确率**，画出成本-质量曲线来定阈值。

## 实验 4-4 ★★：执行工具 MCP 服务器

- **原书位置**：§「执行工具」之后
- **目的**：构建执行工具系统，**重点展示安全机制的实践应用**。
- **工具覆盖**：
  - **文件写入与编辑**：写入后**自动调用 linter 验证语法**，返回结构化错误信息；
  - **终端命令执行**：超时控制、危险命令检测（如 `rm`、`dd`、`curl | sh`）、命令历史追踪；
  - **代码解释器**：沙盒 Python 执行、危险操作审批、长输出总结；
  - **数据操作**：Excel 读写、公式应用、截图生成；
  - **外部系统对接**：日历事件创建、GitHub PR、邮件发送、Webhook 调用；
  - **图形界面操作**：基于 browser-use 的虚拟浏览器（导航、内容提取、截图、处理机器人检测）、虚拟桌面（Anthropic Computer Use）、虚拟手机（Android World）。
- **实验要求**：为这些执行工具添加**完整的安全与验证体系**——文件操作自动 linter（Python/JavaScript 等）、危险命令的 LLM 驱动审查、长输出的截断与持久化。
- 〔精读批注〕把本章 §执行工具 的清单当验收表用：**输入验证 → 权限控制 → 事前审批 → Sidecar 门控 → 自动验证 → 截断持久化 → 沙盒隔离 → 可观测性 → 幂等/预检确认**。逐项打勾并记录「未实现项的失败表现」，比一次做全更能看清每层的真实价值。特别建议测一次**静默截断**（故意不标注省略）看 Agent 会不会基于不完整信息下结论。

## 实验 4-5 ★★：协作工具 MCP 服务器

- **原书位置**：§「协作工具」之后
- **目的**：构建完整的协作工具系统，涵盖**子 Agent 管理、人类协助与多渠道通知**。
- **子 Agent 管理工具**：**创建**（`spawn_subagent`）、**发送消息**（`send_message_to_subagent`）、**取消**（`cancel_subagent`）、**获取结果**（`get_subagent_status`）——支持**同步与异步**两种模式，异步模式立即返回任务 ID、完成后凭 ID 取回。
- **人类协作工具**：**请求管理员协助**（`request_human_approval`、`request_human_input`，关键决策前请求批准或补充信息，**支持超时与默认行为**）；**通知工具**（`send_im_notification`、`send_email_notification`、`send_slack_message`）。
- **实验要求**：设计智能的协作策略——① 为子 Agent 实现**至少两种上下文传递方式**并对比效果（**最小化传递**只传任务参数 vs **LLM 生成上下文**额外调用一次 LLM 从主 Agent 轨迹中提炼交接上下文）；② 编写系统提示词让 Agent 识别**何时需要 HITL**、主动请求确认或输入；③ 实现超时机制与多渠道通知。
- 〔精读批注〕「最小化传递 vs LLM 提炼上下文」是本章最值得量的对照：前者便宜但子 Agent 可能缺关键背景，后者多一次 LLM 调用却能把「为什么做、已知什么、约束是什么」传清楚。建议记录**子 Agent 首次产出可用率**与**来回追问轮数**，这两个指标比总 token 更能说明上下文质量。另外别忘了第 2 章的结论：**任务描述必须自包含**——这正好用实验来验证。
