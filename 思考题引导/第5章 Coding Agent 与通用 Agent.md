### 思考题 1 ★★

> 代码生成被称为 Agent 的“元能力”。但代码执行引入了安全风险——Agent 生成的代码可能包含漏洞、无限循环或资源耗尽。沙盒隔离能解决部分问题，但也限制了代码能力（比如无法访问网络或文件系统）。如何在安全性和能力之间找到最优平衡点？

**提示思路**：先承认这是**能力-风险的连续谱**而非二选一，再逐维设计：网络（默认断网 + 白名单代理按需放行）、文件系统（源码只读挂载 + 独立可写工作区 + 凭证不挂载）、资源（CPU/内存/磁盘配额 + 超时，且超限返回**结构化错误**让 Agent 修正）、凭证（最小权限 + 短时令牌）。可借用本章「隔离层级」（进程/容器/microVM）与「梯度放权」思路：**按任务风险等级选择隔离强度**，并用审计与回滚兜底，而不是一次性把权限开到最大。

### 思考题 2 ★★★

> Agent 自举——能创造 Agent 的 Agent——实现了“智能的自我繁殖”。但每次自举都可能引入新的偏差或错误，这种错误会在代际间累积吗？如何防止 Agent 自举的退化？

**提示思路**：先判断「会不会累积」要分两类：**可验证维度的错误**（协议不合规、工具描述缺失、API 过时——可被自动化检查拦截）与**不可验证的偏好漂移**（架构取舍、提示词风格、隐性偏见——会随复制-变异悄悄固化）。防退化手段可从本章与后续章节借：**范例的版本化与评审**、**基于范例而非提示词穷举**、**每代跑同一批基准做代际回归**（第 7 章）、**保留可回滚的历史与溯源**（第 9 章）、以及刻意引入**异源审核**防止同源盲区累积。

### 思考题 3 ★★

> 代码生成 Agent 在处理日志解析时，能自动跟随格式演化。但如果格式变化是一个 bug 而非预期改动，Agent 的适应性反而掩盖了问题。Agent 应该如何区分“需要适应的变化”和“需要报告的异常”？

**提示思路**：核心是**建立"期望"的显式来源**——从 schema 契约、上游发布记录/变更日志、历史分布基线、字段语义约束中判断"这次变化是否在预期内"。可设计的机制：**变更分类器**（先分类再决定适配 or 上报）、**分布异常检测**（字段缺失率/类型突变/取值越界）、**双轨处理**（自动适配的同时**始终留一条告警与证据**，让人类事后可审计）、以及**灰名单**（未注明来源的格式变化一律先报告）。注意本章的同类原则：**产品模式宽容、训练模式严格**——适配可以自动，但"这是不是 bug"的判断不该由适配方单独做出。

### 思考题 4 ★★

> 本章在 PPT 生成、视频编辑和日志可视化中反复使用提议者-审核者机制。如果 Reviewer 的审美偏好与目标用户不一致，比如 Reviewer 认为信息密度合理但用户觉得太拥挤，反馈循环会收敛到错误的局部最优。如何让用户的偏好反馈也参与 Reviewer 循环？

**提示思路**：把 Reviewer 的判据分成三层：**客观层**（溢出、遮挡、可读性——可自动检测）、**规范层**（品牌/模板/无障碍——可写入 Reviewer 提示词与检查清单）、**偏好层**（密度、风格——**必须来自用户**）。让用户偏好进入循环的方式：把偏好**外化为可复用产物**（用户画像卡/Skill/示例集，第 3 章），在 Reviewer 提示词中显式引用；提供**少量候选供用户选择**（偏好采样）；把用户的接受/修改/拒绝记录成反馈并**回写规则**（第 9 章的学习闭环）；同时防止过拟合——用边界集与保留集（第 1 章模式）验证"改这一条没有破坏其他页"。

### 思考题 5 ★★

> 本章展示了 Coding Agent 把执行和调试中获得的经验沉淀回代码库的多种方式——写入知识库文件、更新架构文档、维护项目指令文件、把操作序列固化为代码。如果把这些经验进一步提炼为系统提示词中的规则，规则集会随时间不断膨胀。如何对沉淀下来的规则做“垃圾回收”——识别并清理冗余或过时的条目？为什么一次成功的代码修改还不能直接视为第九章所说的持续进化？

**提示思路**：垃圾回收可从四类信号入手——**从未被触发**（统计规则命中率）、**已被更底层约束覆盖**（如已写进 linter/类型系统，提示词里那条就是冗余）、**相互矛盾或重复**（定期做语义合并）、**随模型/依赖升级而过时**（第 1 章「适配层清单」的定期复测）。机制上建议：给每条规则**记录来源与引入理由**（可追溯才能判断是否仍成立）、定期做**批量整理**（借第 3 章「定期整理」三项工作）、以及**用边界集+保留集**验证删除不伤性能。至于"一次成功的代码修改 ≠ 持续进化"：单次成功可能是**偶然**（本次任务碰巧对），而进化要求**可复现、可归因、在应改变与不应影响两组样本上都成立**（第 1 章「边界集 + 保留集」、第 9 章评价轨迹后选择更新载体）——且要经过验证、灰度与回滚，而不是直接合入。

### 思考题 6 ★

> “对远程工作友好的团队往往也对 AI Agent 友好。”你所在的团队或组织，在知识文档化方面距离“AI-ready”还有多远？最大的障碍是什么？

**提示思路**：用本章给出的可操作指标自查：**一个远程新人只靠代码仓库和文档，能不能独立开展工作**？逐项核对——决策记录、issue/PR 描述、开发指南、项目指令文件（CLAUDE.md/AGENTS.md）、构建与测试命令是否可复现。障碍通常不在工具而在**激励与习惯**（口头决策、私聊沉淀、文档无人维护）；可提出最小可行的改变（如"PR 必须写清动机与验证方式"）。

### 思考题 7 ★★★

> Simon Willison 提出了 Agent 的“致命三要素”（访问私有数据、暴露于不受信任内容、具备外部通信能力），本章在此基础上增加了第四个——持久记忆。在一个需要同时处理这四种要素的生产环境中，你会如何设计安全策略？

**提示思路**：按「四类边界」逐条布防——**数据边界**（最小权限、只读挂载、凭证隔离、数据层行级安全）；**输入信任边界**（来源标注、指令/数据分离、把外部内容当不可信输入审计、Skill/MCP 描述审查）；**输出影响边界**（网络出口白名单、高风险动作独立授权与人在回路、Sidecar 门控、幂等与预检确认）；**跨会话边界**（记忆写入需与外部内容同等审查、记忆可审计可回滚、防投毒）。再补一层**"即使全被攻破"**的假设：确保任何单点失效都不会造成不可逆损失（沙盒 + 只读凭证 + 数据层最终裁决 + 审计留痕 + 熔断升级人工）。

### 思考题 8 ★★

> Artifact 模式让 Agent 生成 SQL 或前端代码，由数据库和浏览器直接执行，绕过 LLM 处理大量数据。与传统的“Agent 直接给出答案”相比，这种“Agent 生成代码、系统执行代码”的分工有什么优劣？生成的 SQL 可能执行破坏性操作、生成的 HTML 可能包含漏洞，又该如何确保安全？

**提示思路**：**优势**：数据不经过 LLM（避免抄写错误、省 token、延迟低）、结果可复现可审计、产物可复用（图表代码、查询可再次执行）。**劣势**：多了一层"要写对代码"的门槛、错误会以执行结果形式暴露（依赖权限与隔离兜底）、需要额外的执行环境与治理。**安全**：SQL 侧用只读账号 + 语句白名单（只允许 `SELECT`，拒绝 DDL/DML/多语句）+ 参数化绑定 + 查询时间与行数限制 + 可访问表/时间范围限制；HTML 侧用**声明式协议（A2UI 类）**或沙盒 + CSP + 受信任组件目录，避免执行 Agent 生成的任意脚本。注意本章结论：**Artifact 模式缩短数据路径，但不替代权限检查与执行隔离**。

### 思考题 9 ★★

> 将业务规则编码为工具内部基于数据库真值的校验，并用参数设计引导模型在调用前核对政策条件，本质上是用代码结构来约束 Agent 行为。这种“代码即规则”的模式相比自然语言规则有什么优势和局限？

**提示思路**：**优势**：无歧义、确定性强（同输入同输出）、适合多条件布尔组合与时间/跨源校验、可测试可审计、**在不可逆操作前提供最后防线**；参数 checklist 还能把"引导思考"与"守门"分层（前者减少无效调用，后者兜底）。**局限**：规则变更要改代码、发版、测试（变更成本高于提示词）；无法覆盖需要语义判断的模糊条款（"合理""紧急"）；**一旦把政策事实的取值交给模型自报就会失效**（必须查真值）；过度代码化会让 Agent 失去解释与变通能力（"改签而非取消"这类替代方案正是自然语言规则的优势）。所以实践是**分层组合**：提示词负责理解、解释与变通，代码负责守门。
