### 思考题 1 ★★

> LLM-as-a-Judge 使用语言模型评估语言模型的输出。这种 “自我评估” 是否存在系统性盲区——比如模型可能一致地给某种风格的回答打高分，而这种偏好与人类评判不一致？如何检测和校正这种偏差？

**提示思路**：先把「盲区」拆成三个可测的东西：**位置偏差**（同一对候选交换顺序后判决是否翻转）、**长度/风格偏差**（评分与回答长度的相关性）、**同源偏差**（评判者与 Agent 同家族时是否更宽松）。检测手段可以从本章已有的方法里挑：交换顺序各评一次、定期做长度-评分相关性审计、**多源异构评判**并做一致性检查、以及用一小批**人工盲评**做校准锚点。校正则要考虑是改 Rubric（把被偏好的特征显式降权）、改聚合方式（一致性不一致即记平局），还是改评判者构成。最后可以讨论一个更根本的问题：**「与人类评判不一致」本身也需要被度量**——你依赖谁作为人类基线，以及这条基线怎么抽样。

### 思考题 2 ★★★

> 评估数据集的 “防泄漏” 设计至关重要。但在开源生态中，benchmark 数据一旦公开，很快就会被纳入训练数据。这场 “猫鼠游戏” 有终局吗？设计一种从根本上抵抗数据泄漏的评估方法。

**提示思路**：先判断「有终局吗」需要区分两类泄漏——**静态题目被记忆**（可防：参数化实例化、专有附件、组合多源）与**任务分布被拟合**（难防：模型能力真提升了，但你分不清是泛化还是记熟了同分布）。再从本章已有的三种手段往上推一层：能不能让**评估集本身动态生成**（模板 + 随机参数 + 真实数据流），让「记住」在成本上等价于「会做」？能不能把评估**锚在不可预先知道的外部事实上**（当日数据、专有附件、真实执行日志）？能不能引入**可检测**机制（canary 变体：不仅检测泄漏，还定位泄漏批次）？最后可以讨论一个更彻底的思路：**评估「获取与使用信息的过程」而非「答案」**（本章的轨迹前缀协议正是一个雏形）。

### 思考题 3 ★★

> Scale AI 的四准则（基于专家指导、全面覆盖、按重要性加权、评价标准自包含）旨在消除评估的主观性。但某些任务维度（如 “回答是否有帮助”“语气是否恰当”）天然具有主观性。如何为这些主观维度设计可靠的 Rubric？

**提示思路**：核心是把**「主观」分解为「可观察的代理特征」**：不评「是否有帮助」，而评「是否回答了用户真正问的问题、是否给出了下一步可执行的动作、是否在信息不足时说明了不确定性」。可借本章的四准则逐条改造：**自包含**要求把抽象形容词换成可数行为；**全面覆盖**要求同时定义 Pitfall（如「用泛泛的安慰代替具体建议」）；**按重要性加权**允许把这类维度设为 important 而非 essential；**专家指导**则要求先收集该场景下的**判例集**，再用判例定义分档。此外可以设计**两段式评分**（先判「属于哪一种」再判「做得好不好」），以及用**评审者分歧度**本身作为该维度是否可靠的信号——分歧高说明标准还没定清。

### 思考题 4 ★★

> τ-bench 通过模拟真实用户行为来评估 Agent。但模拟用户本身也是一个 LLM——它可能系统性地低估某些边缘场景（如情绪激动、表达不清的用户）。如何验证模拟用户本身的质量？

**提示思路**：把「模拟用户」也当成一个**被测系统**，为它建一套小规模评估：**一致性与可控性**（同一 `user_scenario` 多次运行是否给出可比行为）、**信息透露纪律**（是否严格按 `known_info` 边界，不漏说也不多说）、**抗忽悠能力**（在 Agent 引导下是否提前宣布已解决——本章的「事实锚定」正是为此设计的）、**情绪与耐心**（是否按设定在首次失败后表达不满、是否按上限终止对话）。更关键的是**与真实用户对齐**：用一小批真实对话样本（脱敏后）作为参照，测模拟用户在**表达含糊度、提问方式、拒绝方式**上的分布差异。最后要意识到本章的一条边界——**模拟用户的行为本身会影响评估结论**，所以它需要版本化、需要被报告。

### 思考题 5 ★★

> 配对比较（Bradley-Terry 模型）假设偏好是传递的（如果 A > B 且 B > C 则 A > C）。但人类偏好经常违反传递性。在 Agent 评估中，非传递偏好可能出现在哪些场景？这如何影响排名的可靠性？

**提示思路**：先构造 Agent 场景里的非传递来源——**能力维度不可比**（A 擅长长文写作、B 擅长简洁回答、C 擅长代码，两两比较时谁在「对方的主场」出现谁吃亏）、**风格与任务的交互**（形式化提问偏严谨模型，口语化提问偏活泼模型）、**评价者构成漂移**（用户群体变化导致偏好本身随时间变化）、**并列与平局处理**（把平局强行判成胜负会制造虚假的传递性）。再看影响：非传递性会让「排名」这个一维表示失真，具体表现为**循环胜负**、**对局顺序敏感**（本章实验 7-8 的 Elo 正是在线顺序相关的）、**区间重叠时无法排序**。缓解方向：按任务/能力分维度分别排名、报告置信区间而非单点、用 Bradley-Terry 的扩展（含平局与随机效应的模型）而非强行产出全序。

### 思考题 6 ★★

> 本章区分了 Pass@k 的能力上限与 Pass consecutive@k 的业务可靠性。对于一个单次成功率只有 60% 的 Agent，怎样结合任务的失败成本、重试成本和副作用，决定应该报告哪个指标、取多大的 k？

**提示思路**：把三个因素各自映射到一个决策变量——**失败成本**决定「能不能容忍一次失败」（容忍 → Pass@k 有意义；不能容忍 → 必须看 Pass^k）；**重试成本**决定「重试是否划算」（重试便宜且无副作用 → 报告 Pass@k 并说明重试策略；重试昂贵 → 报告 Pass^k）；**副作用**决定「能不能重试」（不可逆操作 → 本章明确要求**在沙盒或可回滚环境中采样**，并把每次失败都记入可靠性指标）。再叠加任务规模：**Pass^k 随 k 指数衰减**，$p=0.6$ 时 $k=3$ 已降到约 21.6%、$k=5$ 约 7.8%——所以 $k$ 应该由**业务上的「连续多少次不能出错」**反推，而不是随手取值。最后要写清 **$k$ 的口径**（同一任务独立采样 vs 生产流水线连续任务）与是否符合独立同分布假设。

### 思考题 7 ★★

> 本章提出 “观察→假设→实验→验证” 的科学方法。但在实践中，Agent 的行为空间巨大，验证一个假设可能需要数百次评估运行。如何在有限计算预算下最大化评估的信息量？

**提示思路**：可以从本章已有的三处做法里提取原则：① **先小后大**（实验 7-13 先跑 4 项任务判断病因，再决定是否扩到 116 项 × 5 种子）；② **分层抽样而非均匀撒点**（按能力标签/难度分层，优先测失败集中的区域——本章「小而集中的失败簇」正是最高信息量的样本）；③ **配对与共享随机条件**（同一批任务逐题对比，方差远低于两批独立样本，这是最直接的「信息量/成本」提升）；④ **截断与二分**（轨迹前缀二分定位首错，比整条重跑便宜）；⑤ **顺序实验与提前停止**（一个变量一轮，发现无效立即停，不要在无效方向上扩大样本）。还可以引入**信息价值**的视角：优先验证「若结论为真则改动最大」的假设，以及能**同时排除多个假设**的实验设计。

### 思考题 8 ★

> AndroidWorld 小实验中，完整元素树把成功率从 25% 提高到 100%，却把 token 用量推到 2.498 倍；精简后成功率不变，token 降到对照组的 0.506 倍。怎样设计一套自动裁剪规则，既删掉无语义的 UI 节点，又不误删对可访问性、状态验证或后续操作有用的信息？

**提示思路**：本章 H5C 用的是最保守的规则（删掉**不可见、没有文字、也不能操作**的容器节点），可以在此基础上分层设计：**保留白名单**（可交互元素、有文本/无障碍标签的元素、当前焦点、影响状态判定的元素，如开关/选中态/进度/错误提示）→ **删除黑名单**（不可见、无文字、不可交互、纯布局容器、装饰性节点）→ **折叠中间层**（把多层嵌套容器压成路径，只留叶子与有语义的祖先）。关键是要有**验证闭环**：每条裁剪规则都要在一组任务上跑「成功率不降 + token 降」两个指标，并用**边界集**（含可访问性标签、动态状态、罕见控件的页面）检查是否误删。可以进一步引入**分级裁剪**（默认保守 → 效果确认后逐级激进），以及**按任务动态裁剪**（当前步骤只需要某类元素时就只保留那类）。

### 思考题 9 ★★

> τ-bench 的用户模拟采用了 “渐进式信息透露”——不一次性提供所有信息，而是根据 Agent 的提问逐步透露。这种设计如何影响评估结果？如果模拟用户的信息透露策略与真实用户差异较大，评估结论还可靠吗？

**提示思路**：先看它**改变了什么**——它把「需求澄清」从一句提示词的期望变成**必须通过提问获取的硬约束**，因此评估的不再只是「能不能解决」，还包括「能不能问对问题」；这会让**不擅长澄清的 Agent 分数显著下降**（这是有意的区分力），也会让**过度提问的 Agent** 因沟通效率过低而被判失败（本章的耐心上限与 `###STOP###`）。再看**差异带来的失真**：如果模拟用户比真实用户**更配合**（有问必答、不主动打岔），评估会**高估** Agent 的澄清能力；如果比真实用户**更不配合**（情绪化、表述混乱、答非所问），则会**低估**。因此可靠性的前提是**模拟用户的行为分布与真实用户对齐**——这需要把模拟用户当作被测对象（思考题 4），并用真实脱敏对话做分布校准。最后要意识到：**透露策略本身是评估设计的一部分**，应当写进评估报告并可版本化（本章「参考物即评估设计」的同一条道理）。
