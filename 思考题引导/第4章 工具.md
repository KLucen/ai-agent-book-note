### 思考题 1 ★★

> MCP 标准将工具定义从 Agent 框架中解耦了出来。但标准化也意味着复杂的工具交互模式（如流式输出、双向通信、有状态会话）可能难以在标准协议中表达。你认为 MCP 未来最需要扩展的能力是什么？

**提示思路**：先列出「现有协议已覆盖」与「表达不了」的两张清单（工具调用是无状态请求-响应，而流式增量、会话状态、服务器主动推送、长任务进度属于另一类）；再想本章已有的线索：传输层已从 SSE 换成 Streamable HTTP（说明「传输/推送」一直在演进）、资源与工具分离、Skills over MCP 工作组。最后判断哪一类缺口最影响你的场景，并给出扩展方向（而不是罗列愿望清单）。

### 思考题 2 ★★

> 在 MCP 生态中，不同的 MCP 服务器可能提供功能高度重叠的工具。当 Agent 面对多个来源不同但功能相似的工具时，应该如何选择？如果不同来源的同名工具在行为上略有差异（比如一个返回摘要，另一个返回全文），Agent 是否有能力感知并利用这种差异？

**提示思路**：从两条线思考——**系统侧**能做到什么（命名空间/前缀、来源标注、工具描述里写明差异与代价、按能力而非来源做层次化组织、同类工具只暴露一个默认项）；**模型侧**能感知什么（描述里的差异是否被写清、返回值结构是否可比、能否通过一次试探性调用发现差异）。别忘了本章的安全视角：同名工具还有**遮蔽**风险，选择策略要同时防误选与防投毒。

### 思考题 3 ★★

> 本章提出了“执行-验证-反馈”闭环（如写代码后自动运行 linter）。这种“操作后立即自动验证”的模式还可以应用到哪些工具场景？是否存在某些操作，其验证本身的成本或风险超过了操作本身，导致这种模式不可行？

**提示思路**：先横向列举可验证的操作（写配置→加载/启动校验、发邮件→投递回执检查、改数据库→一致性/行数校验、生成文档→渲染截图比对、部署→健康检查与回滚），再逐一评估**验证成本**（时间、算力、副作用）与**验证风险**（验证本身是否也会改变世界、是否可能泄露、是否可能误判）。重点找那类「验证即另一个高风险操作」的情形，并提出替代方案（延迟验证、抽样验证、只做只读断言）。

### 思考题 4 ★★

> 本章提出了“工具爆炸”问题——Agent 面对数千个工具时选择精度下降。除了主动工具发现，还有哪些方案？可以参考人类专家在面对大量可用工具时的策略。

**提示思路**：从人类专家的做法切入：按**领域/场景分层的工具箱**、**常用工具的手边化**、**按任务模板预置工具集**、**专家口头约定（团队惯例 = 提示词/系统约定）**、**求助/转交（找对人而不是找遍所有工具）**。再把每一条映射到工程手段（层次化组织与分类、按会话/任务类型装载工具子集、Skill 组合、把「不知道用什么」显式化为可调用的人类求助工具、以及用**评估**度量误选率来指导裁剪）。最后给出你自己的选择判据。
