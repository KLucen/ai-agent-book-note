### 思考题 2 ★★

> Qwen3 的 Chat Template 思维链保留机制只保留 “最后一个真实用户消息之后” 的思考。如果一个 ReAct 循环跨越了上百轮工具调用，累积的思考内容可能消耗大量上下文。你会如何修改这个机制来应对超长循环？DeepSeek R1 曾要求剥离全部历史思考，而 DeepSeek V4 反转为强制回传全部 `reasoning_content`——对比这两种相反的策略，各有什么利弊？这个反转说明了什么？

**提示思路**：先算清「思考内容的 token 占比」与「思考承载的状态价值」（为什么调用该工具、排除了哪些假设）；再对比三种位置（全剥离 / 全回传 / 中间方案如按轮次或按阶段摘要）在长循环下的收益与风险；最后回到「模型训练分布」这一约束——策略不是自由选择，而是要与模型实际训练过的输入形态一致。

### 思考题 4 ★★

> Agent 状态栏将隐式状态显式化。但如果状态栏本身包含了错误信息（比如工具计数器出了 bug），Agent 可能基于错误的信息做出有害的决策。这种“元信息可靠性”问题如何缓解？

**提示思路**：本章给了两条纪律（尽量用代码维护；用 LLM 时逐条抽取、代码汇总）；在此之上再想三层：**来源可信度**（哪些数据源允许写入状态栏）、**自检/审计**（状态栏与原始记录的一致性校验、异常值告警）、**兜底**（不轻易删除原始上下文，保留可回溯证据）。

### 思考题 5 ★★

> 提示工程消融实验表明，信息组织的混乱导致成功率下降 30% 以上。但在实际开发中，系统提示词往往由多人在不同时间维护。你会用什么工程实践来防止系统提示词的 “熵增”？

**提示思路**：把提示词当代码资产管理：结构化分区（身份/流程/规则/示例）、显式优先级与例外写法（作用域 + 动作 + 例外 + 验证方式）、变更评审与负责人（本章提到产品经理主笔）、变更后跑消融测试、以及缓存边界的稳定性约束（动态内容不得写入前缀）。

### 思考题 7 ★★★

> Skills 的渐进式披露只在 Agent 判断需要时才加载完整内容。但这个判断本身依赖模型的能力——如果模型不知道自己不知道什么，就无法正确触发 Skill 的加载。这个“元认知”问题如何解决？

**提示思路**：从「目录质量」入手（`description` 写成路由条件、给反例、明确何时不该用），再想「外部信号」弥补元认知：用户显式斜杠命令、工具发现的搜索、任务类型/pipeline 的确定性路由，以及用评估度量误触发与漏触发。
