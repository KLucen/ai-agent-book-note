### 思考题 1 ★★

> 共享上下文的多 Agent 协作中，后续 Agent 继承了前序 Agent 的完整上下文。但前一个 Agent 积累的“思维惯性”可能影响后续 Agent 的判断——比如继承了“需求分析师”上下文的“代码审查员”，可能还是倾向于从需求角度思考而非代码质量角度。如何检测和消除这种角色间的干扰？

**提示思路**：先把「角色间干扰」拆成三层可观测的东西——**输入层**（继承的历史里，哪些内容与当前职责无关）、**行为层**（当前 Agent 的工具选择、关注对象、输出结构是否仍贴合上一个角色）、**判据层**（谁来认定「跑偏」：靠人眼，还是靠可检查的断言）。检测可以借助本章已有的对照思路：给同一角色分别喂「全量继承」与「裁剪后的移交包」，比较输出结构的差异；再为每个角色列一组固定检查项，看当前轮是否满足。消除方向要区分这到底是**上下文裁剪**问题还是**规程强度**问题，并注意实验 10-1 已经点出的成本面——裁掉历史是否会破坏静态前缀的可复用性。最后可以追问一句：历史裁掉之后，前序阶段已经确认的事实该以什么形式保留下来。

### 思考题 2 ★★

> 管理者模式中，Manager Agent 负责任务分解和结果整合。但 Manager 本身的能力上限决定了整个系统的能力上限——如果 Manager 无法正确分解任务，子 Agent 再强也无用。如何确保 Manager 的分解质量？

**提示思路**：先把「分解质量」变成可判定的东西——分解产物本身应当满足哪些性质（覆盖原始目标的每一条要求、子任务边界不重叠、每个子任务有可验证的完成标准、依赖关系无环），再挑其中**可以自动检查**的部分写成断言。然后解决「谁来检查」：让独立审核者拿原始需求与分解结果做对照，与让 Manager 自评是两件不同的事，本章「提议者-审核者」一节的判据可以直接借用——审核者读取的是独立证据，而不是复述分解者的解释。工程侧还可以加一道保险：把分解结果**先固化再执行**（计划与执行分离），失败时回退到「重新分解」，而不是让执行者硬扛。最后可以反问一句：什么样的任务其实**不值得**追求高质量分解（分解成本高于收益时怎么办）。

> 去中心化模式借鉴了人类组织的最佳实践。但人类组织也有大量失败模式——沟通不畅、责任推诿、目标冲突。你认为 Agent 社会中最可能出现哪些“组织病”？如何预防？

### 思考题 4 ★★★

> 在管理者模式中，当多个子 Agent 并行执行时，一个子 Agent 的发现可能使其他子 Agent 的工作变得毫无意义（比如搜索任务中一个 Agent 已经找到了答案）。设计一种高效的级联终止机制，实现“一个成功，全员停止”。

**提示思路**：把「一个成功，全员停止」拆成三个必须分别成立的性质——**结算点的正确性**（停止的依据是「已验证成功」还是「声称成功」）、**原子性**（两个几乎同时到达的成功事件只能结算一次）、**传播与收敛**（谁能发终止、经过哪些跳、如何在有限时间内确认所有节点都已停止）。再从成本侧设定取舍：终止信号本身也占带宽与延迟，于是「多久算超时」「超时后是否升级」需要显式策略。本章已经给了三件现成材料——消息总线上的广播、优雅终止与强制终止的两级强度、以及 Go context 式的级联取消；还可以补两个容易被忽略的细节：**部分产物是否需要保留**（已经拿到的资料别一起丢掉），以及**终止之后由谁负责汇报「哪些没跑完」**。

### 思考题 6 ★★★

> 基于市场机制的 Agent 协作（Pinchwork、RentAHuman）引入了交易关系：一个 Agent 花钱雇佣另一个 Agent（或人类）完成任务。那么，雇主 Agent 如何自动衡量执行者交付的结果质量？如果执行者声称已完成但雇主认为质量不达标，争议由谁仲裁？如何防止劣币驱逐良币？

**提示思路**：把「交易」拆成三个可设计的部件——**验收定义**（下单时就把「什么算合格交付」写成可判定条目，而不是事后争论）、**质量度量**（能用可执行验证的就不靠主观评分；必须主观评分时，先回答评分者从哪来、是否与被评方独立）、**争议处理**（仲裁者的选任、证据形式、裁决的成本与时效、败诉方的后果）。「劣币驱逐良币」要从激励结构上看：如果低质量交付被发现的概率低、被发现后的惩罚也低，市场会自己筛掉认真交付的一方——所以至少要有一件东西是**沉淀且公开的**（历史履约记录、保证金、声誉）。最后可以对比一下：这套机制与本章「提议者-审核者」的差别在哪里，为什么在开放市场里安排一个独立审核者比在团队内部更难。

### 思考题 8 ★★

> 人类社会需要多人分工协作，是因为每个人的能力有限——做前端的不一定懂后端，懂设计的不一定会运维。但大模型更像一个“全才”。相关研究表明，在纯文本推理任务上，多 Agent 辩论在等量计算资源下并不优于单 Agent。那么，使用多个 Agent 而非单个 Agent 的真正优势到底在哪里？

**提示思路**：关键是把「多个 Agent」这个词拆开——本章给出的判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息。据此可以把常见做法先分成两组：**只在同一份信息上增加讨论量的**（互相审查、辩论、多角色扮演），与**引入新信号的**（执行结果、渲染截图、外部工具验证、独立采样后的聚合）。第二组里还要再分一次：新信息来自**外部世界**，还是来自**独立的随机性**（同一问题独立采样再投票，靠的是采样多样性而非新事实）。回答时最好举出自己经验里「一个全才模型确实不如一组更弱的 Agent」的场景，并说明它落在哪一组——如果落不进任何一组，它很可能只是多花了算力。

### 思考题 9 ★★★

> 本章将“共享上下文”与“不共享上下文”作为多 Agent 系统的核心设计维度。共享上下文让所有 Agent 看到相同信息，似乎更利于协调。但《三体》中的三体人思维完全透明，技术发展却陷入停滞；回形针思想实验也表明，当群体趋向同一目标时，多样性随之丧失。在多 Agent 系统中，如何在效率与多样性之间找到平衡？

**提示思路**：先把「多样性」具体化——它在多 Agent 系统里至少有三个来源：**模型与提示词差异**、**可见证据差异**（各自看到不同信息、用不同工具）、**职责差异**（目标函数不同）。本章失败模式三说明：只增加实例数而不制造差异，得到的是共因失效而非多样性。再看「共享上下文」这个变量：它提升协调效率的方式是让所有人看到同一份事实，代价恰恰是**抹平证据差异**——于是问题变成「哪些信息必须共享（事实、接口、状态），哪些必须隔离（判断、证据来源、立场）」。可以从已有设计里找现成做法：按角色裁剪信息的信息权限控制、审核者只看原始证据不看提议者的解释、handoff 只传任务包与产物引用。最后请为你的方案设一个可检验指标，否则「多样性够不够」永远只是感觉。

### 思考题 10 ★★★

> 给一个 Coding Agent 分配 30 步预算和 300 步预算，它的工作策略应该如何不同？研究表明，单纯增加步骤预算并不能保证性能提升——Agent 会在浅层搜索后过早“饱和”。设计一种“预算感知”机制，让 Agent 在小预算下快速实现核心功能，在大预算下增加规划、测试和审查环节，充分利用额外的计算资源。

**提示思路**：先把「预算」翻译成 Agent 每轮都拿得到的信号（剩余步数、剩余 token、剩余时间），再规定**不同预算区间对应不同策略档位**——本章提到的做法是前期广泛探索、后期聚焦最有希望的方向，逐步从「广撒网」切到「深挖掘」。设计时要回答四个问题：**谁来估**（模型自估还是运行时统计）、**何时切换**（阈值触发还是连续调节）、**切换什么**（探索/利用比例、是否插入规划与测试环节、是否提前收敛）、**兜底是什么**（预算耗尽时如何交付一个可用但可能不完整的结果）。可以用本章两处素材做交叉验证：预算感知的价值在搜索型任务上最明显；而在有明确验收标准的实现型任务上，多出来的步骤应当转化为测试与审查，而不是继续探索。最后建议设计对照实验，比较「有效步骤占比」而不只看最终成功率。
