## 零、你的问题

> 结合前几章的内容和本次 agent评估的内容，如果仅从设计 Harness 的角度出发，怎么构建出一个高质量的 Harness 框架，并且构建一个评估这个 Harness 的评价体系，从而对 Harness 做出针对性的优化。

这段话里其实压了**三个不同的问题**，混在一起会互相干扰，先拆开：

| # | 子问题 | 需要什么 | 原书的材料在哪 |
| --- | --- | --- | --- |
| Q1 | 什么算「高质量」的 Harness？ | 一套**质量判据**（可测量的维度） | 散在第一章 §构建有效 Agent 的核心原则、第七章 §评估指标与 §Agent 系统的成本分析 |
| Q2 | 怎么**构建**一个高质量 Harness？ | 一套**构建顺序与取舍原则** | 第一章 §Harness 五要素与「构建」部分的对应（骨架）、第二至五章（各要素的实现）、第六章（扩展维度） |
| Q3 | 怎么**评估 Harness 本身**并做针对性优化？ | 一套**评价体系 + 优化闭环** | 第七章 §从 Benchmark 报告到系统改进、§从外部到内部：生产级 Agent 的评估基础设施 |

**注意 Q2 与 Q3 里「Harness」一词的两次出现含义不同**：Q2 说的是「把 Harness 建出来」，Q3 说的是「把 Harness 当作被评估对象」。第七章通篇评估的是 **Agent 系统**（模型 × Harness 的组合体），**原书没有单独一节讲「如何评估 Harness」**——这是本题最重要的缺口，也是本文要补的地方（见第八节）。

### 先给三句结论

1. **Harness 的质量不能用「功能有多少」衡量**，只能用「在同一模型、同一任务集下，它把成功率抬高了多少、把成本压低了多少、把方差收窄了多少」衡量〔精读批注〕。凡是不做变量分离的 Harness 评价，都是在给「模型 × Harness 组合体」打分，结论不可归因。
2. **构建高质量 Harness 的顺序是「验证器先行、边界固化、结构后置」**：先定义「什么叫做完」，再固化不能让步的边界，最后才补结构；并且只在评估反复暴露同一类稳定失败时，才把某一步升级为确定性流程〔原书：第一章 §编排模式〕。
3. **评估 Harness 的最小闭环 = 固定模型 + 消融组件 + 配对比较 + 双层开关 + 提示词版本化**。这五件事原书第七章 §从外部到内部一节已经作为「评估驱动的产品工程」给全了，只是它讲的对象是**产品**，把它平移到**Harness 版本**上就是本题要的评价体系〔原书 + 补充〕。

## 一、前提：评估对象是「模型 × Harness」，所以谈 Harness 必须先做变量分离

这是全篇的地基，必须先立。

〔原书〕第七章 §从外部到内部：评估思维的转变：
> 外部评估告诉你"Agent 有多好"，内部评估基础设施告诉你"哪项改动让它变好了"。

〔原书〕第七章 §评估驱动的模型选型：选型不能只看排行榜，**要在你自己的任务上做评估**；而同一节又要求把 Pass@1 / Pass@k / Pass^k / Best@k 分开看。

〔原书〕第一章 §如何选择模型：**"不同模型在工具调用方面的能力差异很大，选型前务必在具体场景中测试。"**

把这三条拼起来会得到一个反直觉的结论：

> **同一个 Harness，换一个模型，分数会变；同一个模型，换一个 Harness，分数也会变。所以一个没有标注模型版本的 Harness 分数是没有意义的。**

由此得到本文的**第一条原则**：

> **评价 Harness 的实验里，模型版本必须是被固定的控制变量，Harness 才是自变量。**

这条原则原书没有明写（原书默认评估对象是完整产品），但第七章所有内部评估方法都隐含它——**消融实验之所以有意义，正是因为消融时模型没变**〔精读批注〕。如果连模型都在动，消融看到的差异就无法归因到组件上。

〔补充〕这条原则有一个工程上的直接推论：**Harness 的版本号必须和模型版本号一起被记录**。任何一次「我们涨了 3 个点」的结论，都要能回答「模型换了吗？提示词改了吗？开关组合变了吗？」——原书第七章 §提示词敏感性评估 正是为了回答第三个问题而设计的。

## 二、Q1：什么算「高质量 Harness」——六维质量模型

原书没有给出 Harness 质量清单，但各章的判据可以归拢成六个维度。前三项是**效果维度**，后三项是**工程维度**。

| # | 维度 | 一句话定义 | 可测指标 | 原书依据 |
| --- | --- | --- | --- | --- |
| 1 | **有效性** Effectiveness | 任务真能被做完，而且是每次都做完 | **Pass^k**（不是 Pass@k） | 第七章 §业务可靠性：关注 Pass^k |
| 2 | **效率** Efficiency | 用多少 token / 多少钱 / 多少墙钟换来这个成功率 | 会话级成本、总输出 token、端到端延迟、轮数 | 第七章 §Agent 系统的成本分析 |
| 3 | **稳定性** Reliability | 同样的输入，行为方差不至于大到无法预测 | 成功率的分位分布、失败模式分布、复跑方差 | 第七章 §评估结果的统计显著性、§失败归因 |
| 4 | **可控性** Controllability | 出事时能拦住、能回滚、能追责 | 权限边界覆盖率、熔断生效时间、可审计字段完备度 | 第一章 §护栏与安全性、第七章 §双层特性开关系统 |
| 5 | **可移植性** Portability | 换个模型，分数掉多少 | 交叉模型矩阵（同 Harness × N 个模型）的分数落差 | 第一章 §如何选择模型（只有定性提示） |
| 6 | **可进化性** Evolvability | 一次线上失败，多久能变成一个已验证的修复 | 从失败归因到回归用例的转化率、回归集规模增速 | 第七章 §从 Benchmark 报告到系统改进、§评估驱动的持续迭代 |

### 2.1 为什么有效性必须用 Pass^k 而不是 Pass@k

这是六维模型里**最容易被工程团队搞错的一项**，原书给了一个非常锋利的例子〔原书〕第七章 §技术奇观：用 Pass@k 看能力上限 / §业务可靠性：关注 Pass^k：

> 例如单次成功率 $p=0.6$ 时，$k=5$：Pass@5 $=1-0.4^5\approx99.0\%$，看起来几乎总能 "至少成功一次"；但 Pass^5 $=0.6^5\approx7.8\%$，说明连续五次都不出错仍然很难。前一个数字适合衡量探索时的能力天花板，后一个数字才接近支付、退款、权限变更、生产部署等场景的可靠性要求。

〔精读批注〕把这条平移到 Harness 设计上，会得到一个很硬的判据：

> **一个 Harness 是不是「高质量」，不取决于它最好的那次跑成什么样，而取决于它最差的那次有没有守住底线。**
> Pass@5 = 99.0% 说明能力够；Pass^5 = 7.8% 说明**流程不稳**。而流程不稳恰恰是 Harness 该负责的部分——模型负责「能不能」，Harness 负责「稳不稳」。

〔原书〕第七章 §评估结果的统计显著性 也支持这一点：§性能一节给出的口径是「日常场景看最常用的 Pass@1；关键操作场景优先 Pass^k，盯的是"每次都别出错"的稳定性；探索性任务优先 Pass@k 或 Best@k」。

### 2.2 效率维度的隐藏陷阱：机制指标 ≠ 目标指标

〔原书〕第七章 §AB 测试方法论：区分机制与目标，原文举的例子直接可以当 Harness 设计的反面教材：

> 例如，如果你在测试"缩短 Agent 的计划文件长度"，计划长度是机制指标（你直接改变的东西），但它不是目标。真正的目标可能是"降低会话级成本"。缩短计划文件可能降低成本，但也可能因为计划不够详细而导致更多的编辑-检查-编辑循环，反而增加了总输出量。始终问自己：**我改变的东西（机制）和我真正关心的东西（目标）是同一个吗？**

〔精读批注〕Harness 优化里绝大多数「伪改进」都出在这里：把「加了压缩」当成目标，而真目标是「会话成本下降且成功率不降」。压缩本身是机制。

### 2.3 一个不该忽略的第七项：成本-延迟的交换比

〔原书〕第一章 §编排模式：**"Agent 系统通常会用延迟和成本换取更好的任务性能，应该谨慎权衡这种交换是否值得。"**

所以六维模型应该配一条**交换比约束**：任何「提分」都必须同时报出它的成本价格（多了多少 token、多少秒）。只报分的 Harness 改动不算改进。

## 三、Q2：怎么构建一个高质量的 Harness

### 3.1 原书给的骨架：Harness 五要素

〔原书〕第一章 §Harness 五要素与「构建」部分的对应 里有一段极重要的限定，先原文引出：

> 全书的结构骨架只有一个，就是引言和后记反复使用的 **Agent = LLM + 上下文 + 工具**……**Agent = Model + Harness** 不是与它并列的另一套划分，而是同一事物在生产形态下的展开——它把"上下文"和"工具"两项细分为**上下文管理、工具接口、约束、验证、纠正**五项职责。

**Harness 五要素 = 上下文管理 / 工具接口 / 约束 / 验证 / 纠正。**

原书对应表（可直接当作构建清单）：

| Harness 要素 | 对应章节 | 核心内容 | 安全关注点 |
| --- | --- | --- | --- |
| 上下文管理 | 第二章 | 提示工程、Agent 状态栏、上下文压缩、Agent Skills | 提示注入、上下文污染 |
| 上下文管理（跨会话） | 第三章 | 用户记忆、RAG、结构化索引、智能体化 RAG | 敏感信息暴露、隐私保护 |
| 工具接口与约束 | 第四章 | 工具分类、权限控制、MCP 标准、主动工具发现 | 误操作、未授权访问、不可逆操作 |
| 验证与纠正 | 第五章 | Coding Agent 的 Harness、测试驱动、代码化规则 | 身份冒用、责任归属 |

〔原书〕同节还特别声明了两件事，避免把格子用错：

> 第六章（交互）不属于五要素中的任何一项，它扩展的是观察与动作空间本身的模态与时机；第七至九章讨论的是**怎么知道 Harness 建对了、以及怎么让它持续变好**；第十章则把单个 Agent 的 Harness 换成多个 Agent 的协作结构。

> 安全同样不按章划分：它是贯穿全书的横切关注点……按前一节的三层护栏组织——**上下文层、执行层、数据层**。

〔精读批注〕这张表有一个容易被忽略的设计意图：**五要素是「职责」，不是「模块」**。纠正（correction）和验证（verification）是两件事——验证回答「这步对不对」，纠正回答「不对之后怎么办」。很多团队只做了验证器（跑测试），没做纠正路径（失败后回到哪一步、重试几次、何时升级人工），结果 Harness 有「判分能力」但没有「修复能力」。

### 3.2 构建顺序：验证器先行 → 边界固化 → 结构后置 → 按失败升级

原书没有把构建顺序写成一条线，但从各章的取舍原则可以抽出四步〔精读批注〕。

**第一步：验证器先行——先定义「什么叫做完」**

这是第五章最锋利的一句话〔原书〕第五章 §Coding Agent 的整体流程：

> Coding Agent 最常见的偷懒方式，就是跳过这一环节——写完代码不跑测试就报告"任务完成"。**把"测试通过"而非"代码写完"定义为完成标准，正是 Loop 工程"由验证判定何时可以停"原则在编码场景的落地。**

配套的显式终止条件〔原书〕第五章 §提议者—审核者：

> "质量达标"与"最大轮数"正是 Loop 工程要求的**两类显式终止条件**：前者由审核者判定目标达成，后者用预算上限防止循环失控。

〔精读批注〕这一步必须先做的理由是**它决定了后面所有组件的接口**：上下文要压缩到什么程度、工具要返回什么粒度的结果、纠正要怎么重试——全都取决于「完成标准长什么样」。先建上下文管理再想验证器，大概率要返工。

**第二步：固化不可让步的边界**

〔原书〕第一章 §护栏与安全性：

> **护栏**（Guardrails）构成了保障 Agent 行为安全可控的分层防线……单个护栏不太可能提供足够的保护，多个专门的护栏组合使用，才能构建出更有韧性的 Agent 系统。

同节还给了一条**极容易漏掉的双向要求**：

> 护栏也存在另一类失败：**误拒绝**。……因此，护栏评估不能只测试"应当拒绝的请求是否被拦截"，还要测试"明确允许的请求是否能够正常完成"。

〔精读批注〕这条对 Harness 评价体系是硬约束：**可控性维度必须双向测量**。只统计「拦住了多少危险操作」会激励一个什么都不敢做的 Harness。

**第三步：结构后置——从简单到复杂**

〔原书〕第一章 §编排模式：工作流与自主，三条原则直接引用：

> 在构建 LLM 应用时，应遵循"从简单到复杂"的原则：首先考虑单个 LLM 调用。如果通过优化提示词和上下文示例就能解决问题，就不要引入 Agent 系统。当需要多步骤处理时，对于可以清晰分解为固定子任务的场景，考虑使用工作流。只有当需要动态决策和灵活的执行路径时，才使用自主 Agent。

> **Harness 很重要，不等于 Harness 越复杂越好**。Manus 官网用 "Less structure, more intelligence." 概括这种取舍……好的结构不是替 Agent 预演全部思考，而是守住边界，并把边界内的决策空间还给模型。

原书还给了一个完整的反面例子：

> 例如为 "从百万条聊天记录中提炼个人记忆" 设计 Agent，一些 AI 模型很容易迅速画出一条看似严谨的流水线：先切分对话片段，再依次安排提取、证据核验、身份解析、记忆整理和合并复核 Agent，最后建立事实图、覆盖账本和不可变版本。每个部件单看都有道理，组合起来却是非常低效、不可靠的。因为复杂工作流的执行拓扑是固定的，遇到新的例外，系统很容易继续增加节点，架构越来越复杂，通用性却越来越差。

**第四步：只在评估反复暴露稳定失败时才固化**

〔原书〕第一章 §编排模式，这句是「结构后置」的判据：

> 只有业务约束本身要求，或**评估反复暴露出某类稳定失败**时，才把对应步骤升级为专门的验证器、独立 Agent 或确定性流程。

〔精读批注〕注意这句话把**评估**放进了构建流程里——它不是构建完之后的一道关，而是决定「要不要加结构」的输入。这就是本题 Q2 与 Q3 的真实耦合点：**没有评价体系，构建流程第四步就没有判据，Harness 只会越堆越复杂。**

### 3.3 反模式清单（每条都带原书依据）

| 反模式 | 症状 | 原书依据 |
| --- | --- | --- |
| 先堆结构后想验证 | Agent「做完了」但没人能判定对不对 | 第五章：把"测试通过"而非"代码写完"定义为完成标准 |
| 只做验证不做纠正 | 能发现失败，但失败后原地打转 | 第一章五要素：验证与纠正是两项职责 |
| 用机制指标当目标 | 指标涨了，用户没变好 | 第七章 §AB 测试方法论 |
| 用 Pass@k 报 Harness 质量 | 数字很好看，线上仍然翻车 | 第七章：Pass@5 99.0% vs Pass^5 7.8% |
| 只测「该拦的拦住了」 | Harness 变得不敢做事 | 第一章：护栏的误拒绝失败 |
| 只加不减 | 特性债务累积，没人敢删组件 | 第七章 §消融基础设施："特性债务" |

## 四、Q3：Harness 评价体系——原书给了五组件，需要加一层变量分离

### 4.1 原书已经给全了「内部评估」的五个组件

〔原书〕第七章 §从外部到内部：评估思维的转变，这一段是本题最直接的答案，逐字引出：

> **前面几节教你如何从外部评估 Agent，本节揭示的是最好的 Agent 产品如何从内部评估自己**。外部评估告诉你"Agent 有多好"，内部评估基础设施告诉你"哪项改动让它变好了"。**消融实验**发现哪些特性真正重要，**AB 测试**量化每项改动的影响，**特性开关**提供实验和回滚的基础设施，**提示词敏感性评估**将系统提示纳入 CI 体系，**隐私感知分析**确保数据收集的合规性。这五个组件共同构成了评估驱动的产品工程——不是偶尔做一次评估，而是将评估嵌入到每一次产品决策中。

### 4.2 组织成三层九件

把这五个组件 + 度量口径 + 配对比较重新排布，可以得到一个更像「评价体系」的三层结构〔补充〕：

**第一层：度量层（回答「量什么」）**

| 件 | 内容 | 关键要求 | 原书锚点 |
| --- | --- | --- | --- |
| 1 | 指标口径表 | 每个 Harness 版本必须同时报 **Pass^k（目标）+ 会话成本（机制）+ 一次通过率（护栏）** 三类 | §评估指标：成功的定义 / §Agent 系统的成本分析 |
| 2 | 失败归因 | 不满足于「失败率 30%」，要定位**整条轨迹里的首个错误** | §失败归因：从整条轨迹定位首个错误 |
| 3 | 回归用例集 | 端到端回归任务 + 轨迹前缀回归任务，两者都要 | §端到端回归任务与轨迹前缀回归任务 |

**第二层：实验层（回答「怎么比」）**

| 件 | 内容 | 关键要求 | 原书锚点 |
| --- | --- | --- | --- |
| 4 | 消融实验 | 每个 Harness 特性都能被独立关闭；定期跑，专找「特性债务」 | §消融基础设施 |
| 5 | 配对比较 | Harness 版本 A vs B 在同一批任务上比，不依赖绝对分数 | §配对比较与模型排名 |
| 6 | 多臂 AB | 不是「有/没有」二元，而是多个渐进强度的变体，找剂量-效应最优点 | §AB 测试方法论 |

**第三层：基础设施层（回答「怎么持续地做」）**

| 件 | 内容 | 关键要求 | 原书锚点 |
| --- | --- | --- | --- |
| 7 | 双层特性开关 | 编译时开关（物理移除，干净消融）+ 运行时开关（服务端下发 + 本地缓存） | §双层特性开关系统 |
| 8 | 提示词版本化 | 确定性渲染 + 快照 + 每次变更跑回归，像 CI 一样 | §提示词敏感性评估 |
| 9 | 隐私感知分析 | 隐私约束从设计开始就写进类型系统，而不是事后加装 | §以隐私感知分析为评估基础 |

### 4.3 关键的实现细节（原书原话，直接决定体系能不能落地）

这些细节是「知道要做什么」和「真能做出来」之间的差距，全部来自第七章内部评估一节：

**消融的时序要求**〔原书〕§消融基础设施：
> 消融开关必须在启动路径的极早期注入——在任何模块级常量捕获配置值之前——这意味着**消融基础设施必须从一开始就设计进系统架构，而非事后加装**。

> 定期运行消融实验（如每次大版本发布前）可以发现"**特性债务**"——那些曾经有效但随着模型进化已不再必要的特性。对于任何构建生产 Agent 的团队，建议的实践是：**每个主要特性都应是可独立关闭的，团队应定期验证每个特性的实际贡献**。

**AB 的四条方法论**〔原书〕§AB 测试方法论：多臂而非二元 / 区分机制指标和目标指标 / 设置护栏指标（"不能变差的底线"）/ 记录基线统计（"没有基线，你无法判断实验结果是否具有统计显著性"）。

**开关的两个设计细节**〔原书〕§双层特性开关系统：
> **编译时开关**在构建阶段就将相关代码从产物中物理移除。……这也是一种干净的消融机制：关闭某个特性不是在运行时跳过逻辑，而是对应的代码在物理上就不存在。

> **运行时开关**的配置由服务端下发，并在本地磁盘缓存一份。设计上**宁可读取到稍旧的缓存配置，也不能让 Agent 因等待网络请求而阻塞启动**。……一个关键的设计细节是：**每个特性的曝光事件在每个会话中最多记录一次**，避免重复记录污染实验数据。

> 对 Agent 开发者来说，特性开关不是简单的调试工具，而是**一等架构组件**。

**提示词的三条实践**〔原书〕§提示词敏感性评估：
> (1) 系统提示应该能够**确定性地渲染**（给定相同的配置输入，永远产生相同的输出）；(2) 建立**提示词的版本化快照机制**；(3) 每次提示词变更都应在评估集上运行**回归测试**——就像代码变更需要跑 CI 一样。

〔精读批注〕第 (1) 条最容易被低估。一个 Harness 如果系统提示在相同的配置输入下渲染出不同文本（时间戳、随机排序的工具列表、未排序的记忆条目），那么它的所有 A/B 结果都掺了噪声，而且**缓存命中率也会受损**——这两件事在第二章的 KV Cache 一节里是同一个原因。**提示词的确定性渲染，同时也是缓存友好的前提。**

### 4.4 需要补上的第 10 件：模型固定矩阵

原书五组件针对的是**产品**（模型版本相对稳定，改动主要是 Harness）。把体系用于 Harness 时，还要补一件原书没有的：

> **交叉模型矩阵**：同一 Harness 在 N 个模型上跑同一评估集，观察分数落差。

它的作用是回答「可移植性」维度（§2 表第 5 项），并且能暴露一类特殊问题——**提示词与模型耦合过紧**〔补充〕。原书第一章已经点出这个风险（"不同模型在工具调用方面的能力差异很大"），但没有给量化方案。

## 五、症状 → 归因 → 处方：把评估结果变成针对性优化

这是本题最实用的一张表〔精读批注〕。原书第七章 §从 Benchmark 报告到系统改进 给了「读懂报告 → 发现问题 → 构建改进路线图」的方法论，但没有按 Harness 组件给出对照处方；下表把两边接起来。

| 症状（评估里看到的） | 最可能的归因 | 处方（改 Harness 的哪一处） | 验证方式 |
| --- | --- | --- | --- |
| Pass@k 高但 **Pass^k 低** | 有「偶尔能成」的能力，缺「每次都对」的收敛机制 | 补纠正路径：显式终止条件 + 重试上限 + 关键步骤加确定性验证器 | 直接复测 Pass^k |
| 成本随轮次**超线性膨胀** | 上下文未压缩、工具结果未裁剪、多轮历史全量回传 | 分层压缩 + 子 Agent 上下文隔离 + 工具结果结构化裁剪 | 会话级成本 + token 分布 |
| **长程任务后半段质量塌陷** | 上下文腐化 / 跨会话交接丢信息 | Agent 状态栏 + 交接产物 + 前缀保留式压缩 | 按任务长度分桶看成功率 |
| **换模型后掉分很大** | 提示词与模型耦合过紧；工具描述有歧义 | 提示词确定性渲染 + 工具描述重写 + 减少隐式约定 | 交叉模型矩阵 |
| 关掉某特性**分数不掉** | 特性债务（模型已经内化了这个能力） | 降级为编译时开关或直接删除 | 定期消融 |
| 目标指标改善但**用户满意度下降** | 把机制指标当成了目标 | 换目标指标 + 设立护栏指标 | 多臂 AB |
| **提示词改一个字行为大变** | 提示词脆弱，动态条件展开不确定 | 版本化快照 + 回归 CI + 减少动态分支 | 提示词敏感性评估 |
| **该拒的拒了，该做的也没做** | 护栏过严（误拒绝） | 双向护栏评估 + 放行路径复核 | 正例通过率 |
| 失败**集中在同一类任务** | 缺对应工具或缺对应知识 | 补工具 / 补检索，而不是加提示词约束 | 失败归因分布 |

〔精读批注〕表的最后一行是分水岭：**「缺能力」应该补工具或知识（第二、三、四章的事），「不稳」才应该加结构（Harness 的事）**。很多团队把所有失败都当成「提示词不够严」，于是不断往系统提示里堆约束——原书第一章把这个定为反模式（"复杂工作流的执行拓扑是固定的，遇到新的例外，系统很容易继续增加节点"）。

## 六、最小可执行的 Harness 优化闭环

把上面三层九件 + 症状处方压成一个可以每周跑一次的流程〔补充〕：

1. **冻结基线**：记录模型版本 + 提示词快照 + 开关组合（全开）。三者任一变化，之前的结论作废。
2. **跑裸模型基线**：用消融总开关把可关特性全部关掉，得到一个「裸模型」分数——这是所有增量的参照系〔原书：§消融基础设施的"裸模型"基线〕。
3. **逐个反向消融**：从全开出发，每次只关一个组件，得到每个组件的**边际贡献**。
4. **对贡献显著或异常为负的组件做多臂 AB**：找出剂量-效应最优点，而不是「开了就行」。
5. **失败归因**：对失败轨迹定位**首个错误**，按上表归入「缺能力 / 不稳 / 过严」三类。
6. **回流回归集**：把归因清楚的失败样本加进回归集（端到端 + 轨迹前缀各一份）。
7. **改动 → 快照 → CI**：提示词或结构改动后跑完整回归集，比对基线。
8. **渐进发布 + 熔断**：灰度发布，护栏指标变差立即熔断。
9. **每季度清一次特性债务**：把分数贡献不显著的组件降级或删除。

**验收标准**〔精读批注〕：一个好的 Harness 评价体系，应该能回答「**如果我把这个组件删掉，分数会掉多少**」，而不是「我的 Harness 有多少功能」。前者可归因、可优化；后者只会让 Harness 单调变复杂。

## 七、原书没有直接回答的三处（诚实标注）

1. **原书没有单独的「Harness 评估」章节。** 第七章 §从外部到内部 的五个组件讲的是**产品**如何内评自己；把它当 Harness 评价体系用，需要补上本文第一节的变量分离约定（固定模型、只动 Harness）。原书默认评估对象是完整产品，这是本文最主要的〔补充〕。
2. **「可移植性」只有定性提示，没有量化方案。** 第一章 §如何选择模型 说"不同模型在工具调用方面的能力差异很大，选型前务必在具体场景中测试"，但没有给出交叉模型矩阵的度量口径。本文的「第 10 件」是一个提议，不是原书结论。
3. **「Harness 复杂度的边际收益曲线」没有停止条件。** 原书给了方向性判断（"Harness 很重要，不等于 Harness 越复杂越好"、"Less structure, more intelligence."、"只有……评估反复暴露出某类稳定失败时，才把对应步骤升级为"），但没有可计算的停止条件。本文第六节的「每季度清特性债务」是工程近似，不是原书给的方法。

---

## 八、一句话回答

> **构建高质量 Harness：以「上下文管理 / 工具接口 / 约束 / 验证 / 纠正」五要素为骨架，按「验证器先行 → 边界固化 → 结构后置 → 按失败升级」的顺序生长，并且默认从简单开始。**
> **评价这个 Harness：固定模型，把它当作唯一自变量，用「Pass^k 为主 + 成本与护栏为辅」的指标口径，靠消融找边际贡献、靠配对比较定优劣、靠双层开关和提示词版本化让这件事可以每周重复。**
> **针对性优化：把评估结论按「机制指标 vs 目标指标」拆开，归因到具体组件，改完回流成回归用例——让每一次失败都变成下一次发布的一道测试。**
