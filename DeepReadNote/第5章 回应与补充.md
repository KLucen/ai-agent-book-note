## 二、逐条回应

### ① 回应：「测试-修复」循环不是 Loop 工程的同义词，而是它在编码场景里的一次落地

**先给结论**：两者是**上下位关系**，不是并列关系。Loop 工程是**跨轮次的循环设计范式**（发现下一件该做的事 → 执行 → 验证 → 记录进度，由验证器判定何时可以停）；「测试-修复」循环是**这个范式在 Coding Agent 流程里的一个具体实例**——它把「验证」这一步落到了测试套件上，把「停止条件」落到了「测试全绿」上。

**原书对 Loop 工程的定位**（第一章把它放进工程范式演进弧线）：

> 随后出现的 **Loop 工程**（Loop Engineering）又把视野从单次运行扩展到跨轮次的持续自主运转：谁来发现下一件该做的事、何时验证、何时才算真正完成（第十章将结合多 Agent 协作系统展开）。（原书 §「从提示工程到 Loop 工程」）

> 这五个阶段不是替代关系，而是层层包含的：提示工程是上下文工程的子集，上下文工程是 Harness 工程的子集，Harness 工程是 Loop 工程的子集，Loop 工程又是 Graph 工程的子集——单个 Agent 循环正是执行图中的一个节点。（原书 §「从提示工程到 Loop 工程」）

**原书对「测试-修复」循环的定位**（第五章流程的第三步「代码实现与测试」）：

> 把“测试通过”而非“代码写完”定义为完成标准，正是 Loop 工程“由验证判定何时可以停”原则在编码场景的落地。（原书 §「Coding Agent 的整体流程 · 代码实现与测试」）

同一节还有一句把「偷懒」直接对应到停止条件的失效：

> 反过来说，Coding Agent 最常见的偷懒方式，就是跳过这一环节——写完代码不跑测试就报告“任务完成”。（同上）

**所以两者的分工可以这样拆**：

| 维度 | Loop 工程（范式） | 「测试-修复」循环（编码场景的实例） |
| --- | --- | --- |
| 关注范围 | 跨轮次的持续自主运转：谁找下一件事、何时验证、何时真算完成 | 单次实现完成之后的质量收敛 |
| 「验证」由谁做 | 验证器，而不是模型自己 | 测试套件（可自动执行、结果二值） |
| 「何时可以停」 | 由验证器判定目标达成 + 预算上限 | 测试全绿；或达到迭代/预算上限 |
| 失败之后 | 修复或重规划 | 分析原因 → 定位问题 → 改代码 → 重跑测试 |

**Loop 工程的第二类停止条件在第五章另有落点**（提议者—审核者迭代）：

> “质量达标”与“最大轮数”正是 Loop 工程要求的两类显式终止条件：前者由审核者判定目标达成，后者用预算上限防止循环失控。（原书 §「代码驱动的多媒体生成 · 提议者—审核者」）

〔精读批注〕一个便于记住的判别句：**「测试-修复」循环回答的是「这一段代码改对了没有」，Loop 工程回答的是「这个循环凭什么可以停」。** 前者是后者的一个可自动验证的实现；换成没有测试的任务（写文案、做设计），「验证器」就换成渲染后的 Reviewer、评估器或人工门禁——范式不变，验证器换人。

〔补充〕一个容易踩的坑：**「循环能跑」不等于「循环正确」**。第五章把可靠性拆成四层故障（API / 工具 / 上下文 / 控制流），并指出无进展循环的信号是**重复调用指纹**（工具名 + 参数反复出现）——若「测试-修复」循环每轮都在改同一行、报同一个错，它不是 Loop 工程，而是控制流层的死循环，需要的是熔断与终止，而不是再迭代一轮。同一原则也适用于预算：**迭代次数上限应当来自可观测的生产数据，而不是拍脑袋定的配置项**。

### ② 补充：什么是流式响应

**一句话定义**：流式响应是**模型一边生成 token，一边把增量结果推给调用方**，而不是等整段回复生成完再一次性返回。

〔补充〕与之对照的两种形态：

| 形态 | 返回方式 | 首字可见时间 | 总耗时 |
| --- | --- | --- | --- |
| 非流式（一次性返回） | 整段完成后一次性返回 | 约等于总耗时 | 相同 |
| **流式**（增量 / SSE / chunked） | 每生成一小段就推一段 | 首个 token 到达即可见 | 基本相同 |
| 批处理（Batch API） | 异步排队，稍后取结果 | 小时级 | 不计入交互延迟 |

**为什么 Agent 特别需要它**，原书给了两条相互独立的理由：

第一条是**给人看的**——第二章实验观察点之一：

> **流式响应的优势**：流式输出让用户能够实时看到模型的思考过程，包括工具调用的决策和结果的处理。（原书 实验 2-4 观察点）

第二条是**给系统抢时间的**，也是流式在 Agent 中真正的价值——第二章「输出的顺序结构」：

> 模型的输出 token 按固定顺序生成——先是内部思考（`<think>` 标签内），然后是给用户的文本回复，最后是工具调用请求。理解这个顺序对实现流式响应很关键：当 `<think>` 标签出现时可以切换到“思考中”状态；第一个工具调用的参数一经完整生成并通过校验，即可立即开始执行，无需等待模型生成后续的工具调用。（原书 §「从 API 消息到模型 Token · 输出的顺序结构」）

第五章把这条机制直接用作 Coding Agent 的实现技巧：

> 现代 Coding Agent 应充分利用流式响应：第二章在讨论模型输出顺序时介绍了这一机制——第一个工具调用的参数一经完整生成并通过校验，即可立即开始执行，无需等待模型生成后续的工具调用。（原书 §「Coding Agent 的实现技巧 · 并行工具调用、流式执行与级联中止」）

也就是说，**流式把「生成三个工具调用」的等待时间与「执行第一个工具」的时间重叠了起来**——这属于第五章「级联中止」同一段的并行执行话题。

**流式带来的两个代价（原书都点了名）**：

1. **半截输出**：第五章「故障与错误恢复」在流式响应上取三个断点——思考中途、正文中途、工具调用参数中途——并给出三种接续方式（丢弃整轮重发 / 作为末尾 assistant 消息要求接着写 / 追加元指令从断点继续）；半截的工具调用无法以原生结构回传，需先转成文字再补完，拼接后重新解析校验；**若半截输出里已有工具因流式提前执行，续写前要按调用指纹去重**，避免重复副作用〔原书 §「故障与错误恢复」〕。
2. **静默卡死**：流式连接最危险的失败不是断开（会立即报错），而是连接建立成功但数据流停止。SDK 的超时往往只覆盖初始连接，因此需要**独立的空闲看门狗**；可推广为「每个长连接都需要活性信号，而非仅依赖连接超时」〔原书 §「故障与错误恢复」〕。

〔精读批注〕判断一个框架有没有真正把流式用起来，看两件事：**（1）工具是否在参数完整的那一刻就开始执行**（而不是等整轮生成结束）；**（2）流停止时是否有活性检测**。只做了「打字机效果」而没做这两件事的，只是把 UI 变好看了。

### ③ 补充：沙盒在哪里运行、占不占本地内存、Python 与库会不会留在本地磁盘

**先回答「在哪里运行」**：原书把这件事讲成一条**隔离强度递增的选型谱**，沙盒没有唯一位置，取决于你选了哪一级。

> 通用执行工具（如 Python 解释器、Shell 终端）本质上允许 Agent 执行任意代码，需要特别的安全考虑。理想的实现方式是在沙盒环境中运行，与宿主机隔离。这里需要澄清一个常见误区：Python 虚拟环境（venv）不是沙盒。它只隔离包依赖，对文件系统、网络和进程没有任何安全约束，在 venv 中运行的代码照样可以删除任意文件、访问任意网络。（原书 §「执行工具 · 执行环境的隔离与沙盒」）

（对照第四章开头对 Code Interpreter 的定义：**「提供隔离的沙盒环境（sandbox，即与主系统隔离的安全运行空间，代码即使在其中运行出错也不会影响宿主机）」**〔原书 §「Coding 是 Agent 的基础能力」〕。）

原书给出的三级谱系：

| 层级 | 运行在哪 | 隔离到什么程度 | 内存/磁盘归属 |
| --- | --- | --- | --- |
| **进程级** | 直接跑在**本机**（Claude Code、Codex、OpenClaw 都属此类） | 与本地用户同权限，可访问/修改/删除任意文件 | 完全用宿主机的内存与磁盘 |
| **容器**（Docker 等） | 本机内核之上，独立文件系统与网络栈 | 更完整，但与宿主机**共享内核**，内核漏洞可逃逸 | 内存来自宿主机；可写层是宿主机磁盘上的一个目录/镜像层 |
| **microVM / 虚拟机**（Firecracker 等） | 本机之上，但**自带独立内核** | 硬件级隔离，运行完全不可信代码的最强层级 | 虚拟内存、虚拟磁盘（物理上仍由宿主机资源承载） |

原书对选型的口径是：「应根据部署环境和安全需求选择隔离层级——本地开发用进程级机制即可，生产环境或处理不可信输入的场景则需要容器乃至 microVM 级别的隔离」〔原书 §「执行工具」〕。第五章则从**安全兜底**的角度补了三条必须项——网络出口控制（默认断网 + 白名单代理）、文件系统隔离范围（源码只读挂载、凭证类文件根本不挂载进沙盒）、资源限额与超时（CPU/内存/磁盘配额 + 超时，且超限应返回**结构化错误**而非静默杀死进程）〔原书 §「Coding Agent 的安全 · 隔离兜底」〕。

第六章还会补一类更"整机"的形态：**虚拟电脑（VM/容器）与虚拟手机（Android 模拟器）**——可以全天候运行、不与用户抢设备、Agent 操作失败最多让虚拟环境崩溃；Agent 与虚拟环境之间通过**共享文件系统**（如 `/workspace/shared`）交换数据，**以文件路径引用传递而非内容拷贝**〔原书 第六章 §「虚拟身份与隔离执行环境」〕。

---

**再回答你真正想知道的两件事**——这里原书没有正面给答案，以下标注为〔补充〕，属于通用系统工程事实，请与书中观点区分：

**（1）「沙盒运行是调用本地运行内存吗？」**

- **进程级**：是。它就是本机上的一个普通进程，直接吃宿主机的内存（也正因此，失控代码可以耗尽你的内存）。
- **容器**：是同一台机器的内存，由 cgroup 限额约束；容器不会给你"额外的"内存，只是给了一个上限。
- **microVM / 虚拟机**：看到的是虚拟内存，但物理页仍从宿主机内存里分配——所以「不占本地内存」的沙盒在本地部署中并不存在。
- **只有把沙盒放到远端**（云上的沙盒服务、另一台机器）时，内存与 CPU 才真正不落在你本机上——代价是文件往返与网络延迟，且共享目录变成了网络挂载（原书第六章强调的「只传路径不传内容」在这种部署下收益更明显）。

**（2）「沙盒里的 Python 和相关库会保留在本地磁盘中吗？」**

答案取决于**可写层是否持久化**，而不是取决于"是不是沙盒"：

| 情形 | `pip install` 装的东西去哪了 | 下次会话还在吗 |
| --- | --- | --- |
| 进程级沙盒（直接在本机跑） | 直接写进本机的 venv / 用户 site-packages | **在**（这正是它"不是沙盒"的原因之一） |
| 容器，未挂载持久卷 | 写进容器镜像的**可写层** | **不在**——容器销毁即丢，下轮重建镜像后消失 |
| 容器 + 挂载卷/命名卷 | 写进被挂载出来的目录 | **在**（只要卷还在） |
| microVM，根盘非持久 | 写进虚拟磁盘 | 通常**不在**；除非把磁盘镜像或挂载盘做成持久的 |
| 远端沙盒（云沙盒服务） | 写进远端实例 | 取决于该服务的快照/持久化策略，与你的本地磁盘无关 |

〔补充〕实践上的三条经验，供你跑实验时直接套用：

1. **"库持久化"应该由镜像/依赖清单负责，而不是由沙盒的可写层负责。** 把 `requirements.txt` / `pyproject.toml` 写进镜像或在会话启动时重装，才是可复现的做法；靠可写层留下的库，下一次换镜像就没了，且不在任何版本控制里。
2. **需要跨轮保留的只有"产物"，不是"环境"。** 这正是原书第六章共享文件系统的思路：环境可以是临时的，产物以文件形式放在共享目录里，Agent 之间只传路径。
3. **容器的可写层会随会话膨胀。** 反复 `pip install` 且不清理，会让镜像/快照越来越大；资源限额里的**磁盘配额**正是为这类"无限写盘"设的（原书明确把「无限写盘」列为限额要防的对象之一）。

〔精读批注〕把这三问收成一句话：**沙盒决定的是"出错时谁受伤"，持久化决定的是"下一轮还剩什么"——它们是两个正交的设计决策，选隔离级别时不要顺手把持久化也一起定了。** 对你的实验记录最有用的动作是：在"动手记录区"里显式写下**沙盒层级 + 是否挂载持久卷 + 依赖是怎么装的**，否则实验不可复现——这与第五章"回退要可靠"（Git 分支、沙盒环境、快照机制）是同一件事的两面。

## 三、下一步建议

1. **本章的疑问正好指向第 6 章**：你在 ① 里关心的「循环什么时候可以停」，在第 6 章会以**异步与事件驱动**的形式再出现一次——事件循环的安全点、取消、抢占，本质上是在回答「一个持续运转的循环如何在不该继续时停下」。读到 §「事件处理机制」时，可以把本回应 ① 的表格拿来对照：**验证器换成了事件紧急度判定**。
2. **流式那条建议做一次实测**：挑一个你常用的 API，比较「等整轮生成完再执行工具」与「第一个工具参数完整即执行」的端到端耗时差。第 6 章的语音一节会把这个尺度压到毫秒（级联流水线的延迟瀑布，图6-7），届时你会看到同一条"重叠执行"原则在每一级上的形态。
3. **沙盒那条建议落成一张清单**：`隔离层级 / 网络出口策略 / 挂载了什么（只读？凭证？）/ 资源限额 / 依赖如何安装 / 可写层是否持久`。第六章的「虚拟身份与隔离执行环境」会给这张清单补上身份与反机器人（CAPTCHA、住宅代理）两项。
