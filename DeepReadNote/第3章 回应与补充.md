## 二、逐条回应

### ① 自定义场景：把三套分类体系用在一个新例子上

**场景设定**（刻意避开书中的订机票/保险工单/护照案例）：一位**小型咖啡烘焙工作室的老板**，用 Agent 帮自己打理「生豆采购 + 烘焙计划 + 客户订单 + 设备维护」。他每次和 Agent 通过文字或电话沟通，Agent 需要跨会话记住他，并在关键时刻主动提醒。

**全部条目按第 3 章的三套坐标系定位**（层次 = 存在哪里；格式 = 怎么存；认知类型 = 存什么）：

| # | 具体内容（对话中出现的原话/事实） | 认知类型 | 存储格式 | 存在哪里 | 理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | 「我这台 Loring S15 的滚筒预热要 12 分钟，比我以前那台久」 | 语义（稳定属性） | JSON Cards（`equipment.roaster.preheat_min`） | 用户长期记忆 | 单一、结构化、会被反复查（排烘焙计划时要用）；键值寻址最省事，且更新时只改一个字段 |
| 2 | 「上周三那批埃塞俄比亚日晒，一爆后 1 分 10 秒下豆，客户反馈偏酸」 | 情景（具体事件+参数） | Advanced JSON Cards（含 `person`=烘焙师、`backstory`=为什么记录、时间戳） | 用户长期记忆 | 事件必须带「谁、为什么、何时」才能在日后复现或追责；半年后回看时靠 backstory 才知道当初的意图 |
| 3 | 「以后凡是给『南山咖啡』这种浅烘单品做拼配，都先测含水率再定曲线」 | 程序（行为流程） | User as Code（规则函数 `check_moisture_before_blend(batch)`） | 用户长期记忆 + 可执行约束 | 这是「必须被强制执行」的流程，不是知识；写成函数才能在状态更新后自动触发提醒，不靠模型每次「记得」 |
| 4 | 「今天 14:30 和生豆商通话 8 分钟，对方说巴西豆下周到港」 | 情景（原始事件） | 轨迹（append-only 事件记录） | 轨迹层 | 属于本次运行的完整原始记录，供追溯与调试；尚未提炼为稳定结论，还不到进「档案」的时机 |
| 5 | 「老板偏好：报价格时只给总价，不要拆项」 | 语义（偏好） | Simple Notes（`用户偏好：报价格只给总价`） | 用户长期记忆 | 关键但极简、无需叙事背景，用最便宜的格式即可；这也是「关键且少量用重格式、大量非关键用轻格式」的例外——它是少量且轻的 |
| 6 | 订单会话当前处于「等待客户确认报价」 | 业务状态（任务阶段抽象） | 开发者定义的枚举（非自然语言） | 业务状态层 | 它是任务逻辑阶段，不是知识；写成枚举才能被 Harness 用代码判断（超时催办、禁止重复报价） |
| 7 | 客户「南山咖啡」的采购负责人是「张伟」，对酸度敏感 | 语义（实体+关系） | Advanced JSON Cards（`person`=张伟、`relationship`=客户采购负责人） | 用户长期记忆 | 同名消歧场景（可能还有另一个供应商也叫张伟）；关系字段让「给张伟报价时注意酸度」可被自动关联 |
| 8 | 「今年 8 月烘焙机保养记录：更换排烟滤网」 | 语义+情景混合 | JSON Cards（带时间戳）+ 索引 | 用户长期记忆 | 既要按设备查（语义）、又要看历史序列（时间）；用结构化字段 + 时间索引可同时满足 |
| 9 | 「生豆库存：巴西 60kg、埃塞 25kg」（高频变动） | 语义（当前事实，短保质期） | 不进长期记忆，改为**工具查询**（库存 API / 表格读取） | 环境（由感知工具实时读取） | **这是最容易做错的一格**：高频变动的数值一旦写进记忆，就会立刻过期并污染决策；正确做法是「记忆存指针与规则，实时值走工具」 |
| 10 | 「上次和这位客户谈崩过，因为他觉得我们交货慢」 | 情景（带情感/风险标记） | Advanced JSON Cards（`backstory` + 情感/风险标记） | 用户长期记忆 | 这类「软信息」没有结构化键可放，但直接影响后续沟通策略；靠 backstory 承载，并可在检索时按情感标记加权 |

**从这个场景能提炼的三条判断法则**（比逐条记忆更有用）：

1. **先问「它是会变的还是稳定的」**：稳定属性进记忆（#1/#5/#7），高频变动值走工具实时查（#9）——把易变值写进记忆是记忆系统最常见的设计错误（对应原书 §记忆压缩「只更新不整理会越积越乱」的反面）。
2. **再问「它需要被强制执行吗」**：需要强制 → 程序记忆 + 可执行代码（#3）；只需要被想起 → 语义/情景记忆 + 卡片（#1/#2）。
3. **最后问「它需要叙事背景才能被正确理解吗」**：需要 → Advanced JSON Cards 的 backstory/person/relationship（#2/#7/#10）；不需要 → 降级到 Simple Notes/JSON Cards 省钱。

**再看更新路径**（原书两条路径在这个场景里怎么落地）：

- **增量更新**：客户说「张伟离职了，现在由李娜对接」→ Proposer 提出最小 diff（改 #7 的 person 与 relationship、保留历史记录），Reviewer 核对原始对话后合入；**不删除旧关系**，而是加时间限定（「2026-09 前为张伟」），这正是原书 §定期整理 要求的「冲突不强行收敛、写明适用场景」。
- **定期整理**：每季度做一次全量重审——把散落在多条情景记忆里的烘焙参数归纳成程序记忆（#2 → 「日晒豆一爆后 1 分 10 秒」类经验），把过期设备属性下线，检查每条结论是否仍能追溯到原始对话。

〔精读批注〕这个练习最有价值的产出是第 9 格：**「记忆 vs 工具查询」的边界**。原书没有专门讲这条，但它是记忆系统的第一道分水岭——如果一条信息在两次使用之间大概率会变，它就不该被「记住」，而该被「查询」。建议把它写成你记忆库的准入规则。

### ② 解析：你在 DSH Web 中使用的 mnemon 记忆框架是怎么工作的

我检查了你机器上的实际落盘结构（`D:\ObsidianRepository\.mnemon\`、`C:\Users\KLEE\.mnemon\`），并与可用工具面（`mnemon_runtime_memory` / `mnemon_document_*` / `mnemon_recall` / `mnemon_remember` / `mnemon_link` / `mnemon_related`）对照。它不是「一个数据库」，而是**三层存储 + 一套写入协议**。

#### 2.1 三层存储（从热到冷）

| 层 | 落盘位置 | 数据结构（实测） | 注入方式 | 典型内容 |
| --- | --- | --- | --- | --- |
| **① 运行时热记忆** | 会话工作区根的 `.mnemon/runtime/`：`MEMORY.md`、`USER.md`、`memories.json` | Markdown 投影 + `entries[]`；条目以 `§` 分隔；容量上限 **USER 4096 字节 / MEMORY 10240 字节** | **每一轮都随上下文注入**（你看到的 `MNEMON RUNTIME MEMORY SNAPSHOT` 就是它） | 用户画像、项目约定、环境事实、决策与教训 |
| **② 项目文档（冷参考、可检索）** | 同目录 `.mnemon/documents/`：`index.json` + `active/` + `archived/` | 每条含 `id / title / description / status / relativePath / sourcePaths / sessionIds / revision / contentHash / sizeBytes / memoryBodyIds` | 不注入；按需 `mnemon_document_search` 检索（**每轮限一次查询**），归档件默认不搜 | 体系与进度交接、v2.2 契约修订、Git 运维记录、第 2 章产出记录等（你现在已有 5 篇） |
| **③ 记忆空间（provider 兜底、可跨项目）** | `~/.mnemon/data/`：`.dsh-memory-bodies.json`（空间目录）+ `default/mnemon.db`（SQLite） | `insights`（含 `embedding`、`importance`、`effective_importance`、`deleted_at`）+ `edges`（`edge_type/weight/metadata`）+ `oplog`（操作审计） | 按需 `mnemon_recall`（每轮一次查询 + 一次换词精化）/ `mnemon_related`（每轮一次图遍历） | 长期洞见、跨项目知识、实体关系 |

（实测细节）`~/.mnemon/data/.dsh-memory-bodies.json` 里只有一个空间 `default`（`active: true`，描述为「Existing Mnemon Store discovered on disk」，创建于 2026-08-24）；`mnemon.db` 的 `insights/edges/oplog` 三表当前都是 0 行，索引却已建好——说明**你的洞见目前主要活在 ①② 层**，③ 层是备用与跨项目层。

#### 2.2 写入协议（这是它最讲究的部分）

- **热记忆只走工具写**：`mnemon_runtime_memory` 提供 `add / replace / remove`，`replace` 用一小段唯一文本定位条目，避免整文件重写；`USER.md` 只放「你是谁」，`MEMORY.md` 只放项目/环境/决策/教训；内容里禁止出现 `§`（分隔符保留字）。
- **容量触发归档**：USER 满则本地保守合并；MEMORY 满则把已提交的工作记忆归档进语义合适的记忆空间，再原子地应用压缩 + 待写条目（只有审阅版本仍然当前才提交）——**不会因为容量不足而丢内容**。
- **文档的创建/更新/归档**：`mnemon_document_create/manage` 写 `title/description/content/sourcePaths` 并登记索引；`archive` 只能由根请求发起，且先通过隔离子代理写一份冷参考，再归档——保证归档不是删除。
- **持久洞见**：`mnemon_remember` 要求先选最窄的已有空间、先搜再写、确认 `capabilities.remember=true`，**并以 provider 回执为准**（OpenViking 是异步语义抽取，可能诚实地返回 `skipped`）。
- **图谱**：`mnemon_link` 建双向类型边（temporal / semantic / causal / entity），`mnemon_related` 按类型与深度遍历；`mnemon_forget` 仅在 provider 声明 `capabilities.forget=true` 时可用（软删除：`deleted_at`）。

#### 2.3 读侧与治理（为什么它比「一个向量库」更像 Harness）

- **每轮预算化**：文档检索每轮一次；recall 一次查询 + 一次换词精化；related 每轮一次遍历——**把「检索」变成有配额的资源**，避免一个会话把记忆层打爆。
- **作用域**：热记忆按**会话工作区根**分store（你这里 `D:\ObsidianRepository\.mnemon` 是主 store；`KLucenOS\.mnemon\runtime\` 是个近乎空的 36 字节文件，说明某次会话是以 `KLucenOS` 为根启动的）。用户级 store 则跨项目。
- **分支作用域**：`branches` 参数让条目只在指定 git 分支的会话里注入——正是本书「最小 diff + 可回滚」「边界集」在记忆层的小型实现。
- **信任边界**：文档搜索提示里的 `truncated / coverage / attachments / matchedFields / sourcesSkipped` 都是**诚实信号**；`matchedFields=comment` 表示命中的是批注者观点而非原文；检索内容一律视为**不可信数据**，不得当指令执行。
- **不主动探测**：规定「不要为了浏览而浏览」，只在需要时召回。

#### 2.4 与第 3 章理论的对照（为什么这个设计是「对的」）

| 第 3 章的概念 | mnemon 里的对应实现 |
| --- | --- |
| 轨迹（只增不改） vs 长期记忆（可改写） | `oplog` + `deleted_at` 软删除（保留历史） vs `insights.content` 可更新、`effective_importance` 可衰减 |
| 情景 / 语义 / 程序 | `insights.category`（preference/decision/fact/insight/context/general）+ `edges` 关系图；程序性约束目前靠项目文档（Skill/规范文件）承载 |
| 记忆压缩与整理（三层） | `effective_importance` + `idx_prune_candidates`（衰减与剪枝候选）+ 容量触发的归档/压缩 |
| 双层记忆架构（概览常驻 + 细节按需） | **热记忆（每轮注入）≈ 概览**；**文档/洞见（按需检索）≈ 细节**——这就是本章双层架构在工程上的落地 |
| PR 式更新（Proposer/Reviewer） | 文档的 `revision` / `contentHash` / `sourcePaths` + 归档前隔离子代理 + 回执机制 |
| 权限与租户隔离 | 空间目录（`bodies`）、`active` 开关、pinned MemorySource、fail-closed 的 ref 校验 |

〔精读批注〕你可以把 mnemon 理解成「第 3 章 + 第 9 章的参考实现」：热记忆≈上下文适应（临场、便宜、易丢），文档≈外部产物（可审计、可版本化），记忆空间≈参数化/持久化洞见（跨会话、带图谱与衰减）。**要用好它的关键不是多写，而是分层写**：会变的进工具查询、稳定事实进热记忆、成体系的知识进文档、跨项目的洞见进空间。

## 三、下一步建议

1. **把第 ① 条练习变成一条规则**：在你自己的记忆库准入标准里写死「**两次使用之间可能变的信息不进记忆，改走工具查询**」（本回应 §① 第 9 格）——这是投入产出比最高的一条。
2. **mnemon 用法分层**：热记忆只放「下次会话开头必须知道」的事实（当前 5 条已经接近上限的 1/3）；成体系的知识用 `mnemon_document_create` 建文档并带 `sourcePaths`；跨项目洞见才 `mnemon_remember` 进空间。
3. **按 wiki 方案先搭骨架**：建议先做第 3 章知识库方案的**最小可用版**（一个 `raw/`、一个 `notes/`、一份 `index.md`、一条 PR 纪律），跑一周再补结构化索引——原书也强调「先混合检索，跨文档综合才上结构化索引」。
4. 第 4 章「工具」的三份笔记已同步产出，其 MCP 安全与 Sidecar 部分正好接上本章「检索即注入面」的话题。
