## 二、逐条回应

### ① 补充：Transformer 是什么，KV Cache 从哪来

**先给结论**：Transformer 是当前几乎所有大语言模型的底层架构，它的核心是**自注意力（Self-Attention）**——处理某个 token 时，同时参考序列中所有已生成 token 的信息。KV Cache 正是自注意力机制的一个必然推论：既然是「同时看前面所有 token」，那就把前面 token 算过的中间结果（Key、Value）缓存起来复用，避免每生成一个 token 就把整个前缀重算一遍。

**〔补充〕Transformer 的最小结构**（原书不展开，这里补齐）：

1. **输入与位置**：token 先变成嵌入向量，再叠加位置信息（否则模型无法区分顺序）。
2. **自注意力层**：每个 token 生成三个向量——Query（我在找什么）、Key（我能被怎样匹配）、Value（我的内容）。用 Query 与所有 Key 做点积得到注意力权重，再对 Value 加权求和（原书 实验 2-2 的「北京的天气怎么样」就是这套流程的直觉版）。
3. **多头注意力**：并行跑多组 Q/K/V，各自关注不同关系（语法、指代、语义等），再拼接。
4. **前馈网络 + 残差连接 + LayerNorm**：逐 token 的非线性加工与稳定训练。
5. **层叠**：以上一块叫一层，现代模型堆叠数十到上百层，第 1 层的输出喂给第 2 层，层层递进——**这正是「改一个 token，后面全失效」的原因**：

> 如果第 k 个 token 发生变化（比如系统提示词改了一个字），k 之前的状态不受影响，但从 k 开始的表示会逐层受到影响——实际复用时，缓存只能保留到首个不同 token 之前，从该位置起需要重新计算。（原书 §「KV Cache 的原理与约束」）

6. **两阶段推理**：**prefill**（一次性处理输入的全部 token，是计算密集的并行阶段）→ **decode**（逐个生成输出 token，是访存密集的串行阶段）。KV Cache 同时优化这两个阶段：prefill 阶段缓存输入 token 的 K/V，decode 阶段只需为新 token 计算 K/V 并追加。

**〔补充〕为什么 KV Cache 会变成瓶颈**：缓存本身要占显存，且大小随「上下文长度 × 层数 × 每层 KV 维度」线性增长；decode 阶段每一步都要读一遍全部缓存（显存带宽受限）。工程上的常见缓解手段有 MQA/GQA（多个查询头共享少量 KV 头）、分页式 KV 管理（PagedAttention）、前缀共享（RadixAttention/Prompt Cache）等。原书只讲清「省掉了重算、省不掉遍历」这一条主线，其余属于推理引擎细节：

> KV Cache 省去的是历史 token 的 K、V 投影重算，使每步解码不必重算整个前缀；但每个新 token 的注意力计算仍要遍历全部缓存的 K、V，计算量随上下文长度线性增长——这正是长上下文解码越来越慢、KV Cache 的显存与带宽成为推理瓶颈的原因。（原书 §「KV Cache 的原理与约束」）

〔精读批注〕把「模型是一层层串起来的」这句话记住，本章后面所有缓存规则（前缀不动、改动越靠前越贵、压缩尽量靠后批量做）都不需要再理解原理，直接可推。

### ② 回应：位置偏好（Position Bias）

你摘录的是原书 实验 2-2 的结论之一，完整上下文是四条注意力模式之一（另三条：注意力储存池、思考的三角形、输出的三角形）。

- **原书给的现象与工程结论**：模型对上下文**开头与结尾**分配更高注意力，中段更容易被忽视，因此「把最关键的信息放在开头或结尾是一项重要的实践原则」〔原书 实验 2-2，引 Lost in the Middle, TACL 2024〕。
- **〔补充〕为什么会这样（几种主流解释，尚无定论）**：① 训练数据里「开头（系统指令/问题）」与「结尾（最近上下文）」天然更重要，模型学到这种先验；② 因果注意力下，越靠后的 token 参与越多次前向计算，等于被「重复曝光」；③ RoPE 等位置编码在长距离上衰减，首尾距离相对更近；④ softmax 的归一化压力导致首个 token 吸收多余权重（Attention Sink），与中段衰减共同作用。
- **对本项目有用的三条操作**：
  1. **状态栏放在轨迹末尾**——这正是原书的设计（借 user 角色追加），既拿注意力又不动缓存〔原书 §「Agent 状态栏在上下文中的具体位置」〕；
  2. **压缩时不要把关键决策压到中段**——压缩后信息密度变高，但位置同样重要；建议「决策/约束/失败/引用」尽量落在首尾可达处；
  3. **评估位置敏感性**：同一内容放开头 / 中段 / 末尾做 A/B，是实验 2-2 的延伸用法（[[实验解读/第2章 上下文工程]] 动手记录区已列为待测项）。

### ③ 你要的对比表：KV Cache vs「缓存命中」（Prompt Cache）

先澄清一个容易混淆的用词：日常说的「缓存命中」在 Agent 语境下通常指**跨请求的 Prompt Cache 命中率**，而 KV Cache 是它底层复用的机制。两者的关系是「同一原理、两个层级」。

| 维度 | KV Cache | Prompt Cache（常说的「缓存命中」） |
| --- | --- | --- |
| 归属层级 | **模型内部/推理引擎**的一次推理过程 | **API 服务商/推理引擎**跨请求的优化 |
| 优化对象 | 单次请求内逐个生成 token 时的重复计算 | 多次请求之间**相同前缀**的重复计算 |
| 生命周期 | 一次请求（或一个会话的持续推理） | 跨请求，按服务商策略保留（分钟～小时级） |
| 复用前提 | 前缀 token 序列不变 | 请求前缀**字节级**相同 |
| 失效条件 | 首个不同 token 之后全部失效 | 同上（前缀变体导致缓存键不同，如动态时间戳） |
| 谁负责 | 推理引擎自动管理 | 部分厂商自动启用、部分需显式声明，计费规则各异 |
| 成本量级 | 省掉重算，但每一步仍需遍历全部缓存（访存瓶颈） | 读取成本约为首次计算的 **1/10**〔原书 §「KV Cache 与 Prompt Cache」〕 |
| 典型可观测指标 | 首 token 延迟（prefill 耗时）、显存占用 | **缓存命中率**、计费单中的 cached tokens |
| 本章对应设计 | 状态栏追加末尾、压缩批量做、工具 schema 追加末尾 | 缓存边界划分、子 Agent 字节级对齐、替换字符串冻结 |
| 一句话记法 | 「同一轮内不重复算」 | 「跨轮次不重复算」 |

〔精读批注〕两个概念容易混，是因为它们共享同一条物理约束（前缀不变性）。工程判断顺序建议：**先设计前缀**（把稳定内容前置、动态内容后置）→ 再看跨请求命中率 → 最后再考虑压缩（压缩必然付一次前缀重建代价）。

### ⑥ 回应：状态栏本质（你摘录的那句）

你的摘录抓住了要害。补一层「为什么这就够了」的机制链条，方便你以后自己推导：

1. **前提**：上下文学习更像检索，而不是推理——模型擅长「捞出已有内容」，不擅长「当场统计归纳」（原书 §「上下文学习的内部机制」）。
2. **后果**：任何「关于上下文的结论」（共几次、是否超限、进展到哪）每次都要**现算**，成本随上下文增长而增长，且容易出错。
3. **对策**：把这些结论**提前算好**，以极低 token 成本放进上下文——这就是状态栏（加结论）与压缩（换结论）的同一枚硬币两面。
4. **收益（实验 2-8）**：小模型准确率接近前沿大模型；**每次迭代的思考 token 量、延迟、花费降低约一个数量级**，且思考量从「随上下文增长」变为「基本恒定」。
5. **代价与新风险**：状态栏是**有损投影**（只算了你预想的维度），且模型**几乎无条件相信**它——所以必须「用代码维护」并防投毒〔原书 §状态栏维护部分〕。

### ⑦ 重点答疑：状态栏两种实现的公式到底怎么来的

你的疑问有两个：**「两次更新间新增后缀 R」是什么**、**两个公式怎么来的**。下面从物理过程推一遍。

#### 7.1 先把场景固定下来

Agent 正在多轮执行：每一轮都会产生新的消息（用户消息 / 模型回复 / 工具结果），并在末尾注入一条状态栏。设：

- $S$ = **一条状态栏本身**的 token 数；
- $R$ = **两次状态注入之间新增的消息**的 token 数（这就是「新增后缀」：状态栏后面到下一次注入前长出来的那一段轨迹）；
- $N$ = 整个会话里状态栏**更新（注入）的次数**；
- $\alpha$ = 缓存命中价 / 正常输入价（原书取 $\alpha \approx 0.1$，即缓存读取约为正常价的 1/10）。

「忽略两种方案共有的成本」指的是：**每轮都写一条新状态栏（$S$ 个 token 的写入）**这件事两方案都要做，所以比较时不计。

#### 7.2 实现一（每轮替换）：删掉旧状态 ⇒ 后缀失效

- 物理过程：每次调用前，把**上一条状态栏从消息列表中移除**，再把最新状态栏追加到末尾。
- 关键机制：从一个位置移除消息，会让**该位置之后**的所有内容缓存失效（前缀不变性）。
- 状态栏原来在末尾，它后面只有「上一次注入之后新增的那 $R$ 个 token」——所以每次替换的损失是：**这 $R$ 个 token 需要按正常价重算，而不是按缓存价读取**。
- 单次损失 $=(1-\alpha)R$；一个会话里有 $N-1$ 次更新（第一次注入无旧状态可删）⇒

$$C_{\text{替换}} \approx (N-1)(1-\alpha)R$$

#### 7.3 实现二（持久追加）：不删旧状态 ⇒ 陈旧状态被反复重读

- 物理过程：状态栏一旦注入就永久保留（Claude Code 的 `<system-reminder>` 即此法），每轮只在末尾追加新的。
- 好处：**只追加不改动**，从不触发失效，前缀始终稳定。
- 代价从另一个地方来：**旧的、过时的状态栏留在上下文里，会在后续每一轮被重新读取一遍**（按缓存价 $\alpha$ 付费）。
- 累计读取量：第 1 条状态被读约 $N-1$ 次，第 2 条被读约 $N-2$ 次，……最后一条 0 次。总读取 token 数 $\approx S\cdot(N-1)+S\cdot(N-2)+\dots = S\cdot\frac{N(N-1)}{2}$；乘上缓存单价 $\alpha$ ⇒

$$C_{\text{追加}} \approx \alpha S\,N(N-1)/2$$

#### 7.4 分界条件

比较两者、两边同时约掉 $(N-1)$（设 $N>1$）：

$$\alpha S N/2 < (1-\alpha)R \;\Longrightarrow\; \text{选实现二（持久追加）}$$

**怎么读这个不等式**（这是最实用的部分）：

| 条件变化 | 倾向 | 直觉 |
| --- | --- | --- |
| 状态栏小（$S\downarrow$） | 实现二 | 旧状态不占地方，留着更便宜 |
| 更新次数少（$N\downarrow$） | 实现二 | 没有多少陈旧状态可累积 |
| 两轮之间消息多（$R\uparrow$） | 实现二 | 删除状态要重算一大段后缀，代价高 |
| 状态栏大（$S\uparrow$）、更新频繁（$N\uparrow$）、后缀小（$R\downarrow$） | 实现一 | 反复重读陈旧状态太贵；此时删掉它只损失很短的后缀 |

**数值算例**（$\alpha=0.1$）：

- 例 A：$S=200,\;R=2000,\;N=10$ → 左 $=0.1\times200\times10/2=100$，右 $=0.9\times2000=1800$ ⇒ $100<1800$，**选实现二**。
- 例 B：$S=2000,\;R=500,\;N=50$ → 左 $=0.1\times2000\times50/2=5000$，右 $=0.9\times500=450$ ⇒ $5000>450$，**选实现一**。

〔精读批注〕这个模型的价值不在精确（原书也说未计上下文占用与陈旧状态带来的歧义），而在于它把「感觉」变成了**三个可测的量**：你的状态栏多大（$S$）、两轮之间轨迹多厚（$R$）、会话预计更新多少次（$N$）。落地时建议：先用日志量出 $S$ 与 $R$，再用真实计费单校正 $\alpha$，最后按不等式选实现——这比争论「追加还是替换」有效得多。
