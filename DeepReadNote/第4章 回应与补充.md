## 二、逐条回应

### ① 补充：什么是异步回调

**一句话定义**：异步回调是「**先登记一个函数（回调），等某件事发生时由系统回来调用它**」的编程模式——调用方登记完就立刻返回、继续干别的，不阻塞等待结果。

**为什么叫「异步」**：与**同步调用**相对。同步是「我调用你，站在这里等你返回」；异步是「我告诉你事情办完后通知我，我先去忙别的」。**为什么叫「回调」（callback）**：控制权是**反向**的——不是调用方去取结果，而是被调用方（或事件源）**回头调用**你提供的函数。

〔补充〕几种容易混淆的近亲：

| 概念 | 谁触发 | 典型形态 | 与异步回调的关系 |
| --- | --- | --- | --- |
| 同步调用 | 调用方 | `result = f()` | 阻塞等待，无回调 |
| **异步回调** | 被调用方/事件源 | `f(callback)`，`callback(result)` 稍后被调用 | 本条目 |
| Promise / async-await | 调用方 await | `await f()` | 回调的语法糖，本质仍是异步完成通知 |
| 轮询（polling） | 调用方反复问 | 每 5 秒查一次状态 | **反模式**：浪费请求、延迟不确定 |
| Webhook | 外部系统 | 事件发生时 POST 到你的 URL | 跨进程/跨网络的回调，本质相同 |
| 事件监听 / 消息队列 | 事件总线 | `on("event", handler)` | 一对多、可持久化的回调机制 |

**在 Agent 里的落点**（这正是原书把事件触发工具放到第 6 章的原因）：

- 第 4 章 §工具的分类 明确：事件触发工具涉及**两个时刻**——**注册**时由 Agent 主动调用工具声明自己关心什么事件；**触发**时由外部事件异步回调唤醒 Agent〔原书 §「工具的分类」〕。这里的「异步回调」就是：定时器到点了、监控的后台命令结束了、外部系统发来 Webhook，系统据此**新起或唤醒一次 Agent 运行**。
- 因此第 6 章讲的「异步与事件驱动」，本质是把 Agent 的主循环从「用户问一次、Agent 答一次」改成「**外部事件可以随时注入一条新观察**」。

〔补充〕工程上最常见的四个坑（自己实现时会遇到）：

1. **重复投递与幂等**：回调可能重发，处理函数必须幂等（与第 4 章执行工具的幂等性同源）；
2. **乱序**：事件到达顺序未必等于发生顺序，需要时间戳/序列号来定序；
3. **超时与重试放大**：回调失败要重试，但必须区分主链路与辅助链路（第 5 章会讲「后台调用失败直接放弃」）；
4. **背压**：事件洪峰时要有队列与丢弃策略，否则 Agent 被事件淹没。

〔精读批注〕一个实用的判断句：**如果你在写「每隔 N 秒查一次」的循环，通常说明你缺一个异步回调（或 webhook）通道**。反过来，如果事件源根本不支持推送，轮询就是唯一选择——此时要把「轮询间隔」当成成本-延迟的取舍参数，并做好去重。

### ② 回应：工具描述的艺术（你的总结是对的，这里补三层精度）

你的总结抓住了原书的三根支柱：**何时用 → 边界 → 示例**。补三点精度：

**（1）「何时用」要用条件式表述，而不是功能式表述。** 原书的对照是：说「搜索相关内容」远不如说「**当需要获取实时信息或查找未知事实时使用**」——前者描述功能，后者帮模型做**调用决策**〔原书 §「工具描述的艺术」〕。

**（2）边界里最值钱的是「负面清单」。** 原书给了一句很硬的话：

> 清晰列出工具的边界条件——做不到什么、不接受什么输入——往往比描述能力本身更重要，因为大多数工具调用失败的根因不是模型不知道工具能做什么，而是不知道工具不能做什么。（原书 §「工具描述的艺术」）

**（3）示例之所以有效，是因为它承载 JSON Schema 表达不了的隐式约定**：时间戳是秒还是毫秒、过滤条件如何嵌套、参数组合的典型形态。原书给的量级是「加入示例后准确率往往明显提升——在一些基准上可从约 72% 提升到 90%」。

另外两条你笔记里没有、但同样实用的：

- **返回值与代价也要写**：返回结构的字段说明能减少解析错误；耗时工具注明「需下载完整网页，可能 5–10 秒；只要元信息可用 `get_page_metadata`」有助于模型规划顺序。
- **调试顺序**：

> 当 Agent 频繁选错工具时，应优先检查工具描述而不是怀疑模型能力。（原书 §「工具描述的艺术」）

〔精读批注〕把这条总结成一句可执行的话：**工具描述是「给模型的 API 文档」，而模型只在复杂任务里分出一小部分注意力读它**——所以宁可写具体例子、负面清单和代价，也不要写抽象规范。

### ③ 回应：MCP 与 Skill 的分发机制（你的摘录准确，三点补充）

先确认你的理解：**MCP 统一的是「专用工具」这种能力的接入方式（协议）；Skill 的分发机制是「注册表」（registry），不需要协议**——`npx skills add <owner>/<repo>`、ClawHub 都属于注册表。

补充三点：

**（1）成本差是选型的硬依据。** 接入一个 MCP 服务器，是在运行时建立连接，它暴露的**全部工具定义会进入每一次会话**的上下文；安装一个 skill 只是往磁盘拷一个文件夹，**常驻上下文的只有目录里的 `name` 和 `description`，token 成本便宜一到两个数量级**〔原书 §「工具生态」〕。

**（2）危险系数相反：Skill 更危险。** 原书明确：

> Skill 的危险系数要比 MCP 大得多。（原书 §「工具生态」）

原因：MCP 传的是工具描述与调用协议，而 Skill **还包含实现代码**，一部分代码可能运行在用户电脑上——可插恶意代码、可供应链攻击、可运行时下载恶意代码。所以用第三方 Skill 要在隔离环境中、尽量不处理敏感信息。

**（3）两条渠道正在合流（否则容易误以为它们互斥）。** MCP 官方已在推动 **skill 经由 MCP 被发现和传递**：同一个 skill 既可躺在 Skill Hub 等 `npx` 安装，也可由一台 MCP 服务器供给〔原书 §「Skills：把工具发现变成按需查阅」〕。

〔精读批注〕一条清晰的选型口诀：**稳定的底层操作 → 专用工具（走 MCP，要审计描述与版本）；频繁变化或需要人改的能力 → Skill（走注册表，要隔离与审查代码）**。这与原书「四决策维度」（安全权限 / 参数复杂度 / 变更频率 / 模型能力）里的「变更频率」一栏直接对应。
